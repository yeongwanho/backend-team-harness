# 테스트가 왜 실패했는지 전달하기

이전에는 복구 요청에 실패한 테스트 이름만 남는 경우가 있었습니다.
이제 JUnit 보고서가 알려 주는 일부 표준 예외 종류도 함께 전달합니다.
예를 들어 다음 정보는 XML 파싱 중 오류가 났다는 뜻입니다.

```json
{
  "code": "xml_parse_error",
  "exceptionType": "org.xml.sax.SAXParseException"
}
```

이 정보는 `bth diagnose <id> <project> --json`의 실패 테스트와 다음 구현
요청의 `recovery.failedGates[].failedTests[].diagnostics`에서 확인할 수 있습니다.
새로 실행한 검증 보고서부터 수집합니다. 옛 기록에 없던 내용을 만들어
넣거나 이전 기록을 덮어쓰지 않습니다.

보고서의 긴 메시지·stack trace·응답 본문은 복구 요청에 복사하지 않습니다.
등록된 표준 예외의 **정확한 종류와 코드**만 전달하며, 알 수 없는 회사별
예외는 추측해 분류하지 않습니다. 실패 여부와 테스트 수는 그대로 남습니다.
테스트당 최대 4종, 입력 최대 32항목으로 제한하고 중복을 제거합니다.

예외 종류가 원인 판정을 대신하지는 않습니다. XML 파싱 오류는 실제 XML이
잘못됐거나 HTML에 XML 전용 assertion을 쓴 경우 모두에서 생길 수 있습니다.
AI는 실패한 테스트와 프로젝트 코드를 확인해야 합니다. 이 필드는 보고서에서
온 미신뢰 진단 정보이지 명령, 자동 수정 규칙 또는 통과 권한이 아닙니다.

수정 후에는 같은 필수 테스트를 새로 실행합니다. 테스트 삭제·skip·검증 기준
완화로 오류를 숨기는 것은 허용하지 않습니다. 재시도 횟수도 기존에 승인한
예산을 따릅니다. 이 개선만으로 자동 복구 성공률이 높아졌다고 보장하지 않습니다.
