# 코드 검색 개선: 무엇을 채택하고 무엇을 버렸나

하네스가 처음부터 알맞은 파일을 골라 주지 못하면 모델이 다시 저장소를 뒤져야
한다. 이번에는 그 앞단의 **파일 후보 검색**을 고쳤다. 실제 구현 성공률이나
전체 개발 속도가 개선됐다는 판정은 아직 아니다.

## 채택한 변경

- `read_account_by_id`를 한 덩어리로만 보지 않고 `read`, `account`, `id`로도
  찾는다. `HTTPServer` 같은 약어와 대문자가 섞인 이름도 나눈다. 원래 이름은
  함께 유지한다.
- 사용자가 `RefundPolicy`처럼 코드 이름을 직접 쓰면, 그 이름의 파일/대표
  선언을 단순히 import한 파일보다 우대한다. 일반적인 `refund policy`라는
  문장에는 이 가산점을 주지 않는다.
- 모든 파일의 단어 집합을 끝까지 보관하지 않고, 질문과 겹친 단어만 보관한다.
  질문에 검색할 단어가 없으면 파일 메타데이터 분석을 생략한다.
- 기존 그래프 연결 점수, 문맥 한도, 관련 테스트 동반 선택, 승인과 검증 권한은
  바꾸지 않았다. 검색 결과는 여전히 참고 자료이며 PASS나 테스트 생략을
  결정할 수 없다.

단어 빈도 계산을 분리한 작은 모듈로 옮겼다. 새 라이브러리·모델·임베딩 서비스는
추가하지 않았고, 그래프 인덱서나 비밀 파일을 읽는 범위도 늘리지 않았다.

## 먼저 시험했다가 버린 방식

파일 이름·디렉터리·참조 이름을 따로 계산하는 BM25F 계열의 후보를 먼저 시험했다.
평균 탐색률은 좋아졌지만, Pet 업데이트의 핵심 파일을 찾던 결과가 1 → 0으로,
이메일 변경 과제도 2/7 → 1/7로 나빠졌다. 따라서 **이 후보는 적용하지 않았다.**

계산 구조의 참고 자료는 [Microsoft Cambridge의 TREC-14 논문](https://trec.nist.gov/pubs/trec14/papers/microsoft-cambridge.enterprise.pdf)이다.
논문이 있다는 사실은 우리 코드 검색에서도 효과가 있다는 증명이 아니다.
이번에 채택한 방식은 그 후보가 아니라 기존 이진 단어 IDF에 식별자 인식만
좁게 보강한 방식이다. 버린 후보의 [소스](artifacts/v28/rejected-fielded-prior.txt)도 남겼다.

## 같은 20개 과제에서의 결과

Spring·NestJS·FastAPI 공개 저장소의 기존 20개 과제를 같은 기준 커밋, 같은
그래프, 같은 질문, **2,000자 코드 문맥 한도**로 비교했다. 모두 계획 생성에
성공했다. 과제별 수치는 [비교 기록](artifacts/v28/retrieval-comparison.json)에 있다.

| 측정값 | 기존 | 채택한 변경 |
|---|---:|---:|
| 상위 5개 평균 Recall | 36.82% | 46.82% |
| 상위 20개 평균 Recall | 43.65% | 51.15% |
| 상위 20개 평균 nDCG | 0.3767 | 0.4503 |
| 정답 파일을 하나도 못 찾은 과제 | 4개 | 2개 |

Recall은 당시 정답 변경 파일을 얼마나 찾았는지, nDCG는 그 파일을 얼마나
앞에 놓았는지 보는 수치다. 문자 한도 때문에 실제 후보는 20개 미만일 수 있다.

나빠진 점도 있다.

- FastAPI DB 설정 과제에서 `.env` **파일명**이 후보 밖으로 밀려 Recall이
  4/6 → 3/6으로 감소했다. 주요 설정·DB·migration 연결 파일은 남았다.
  `.env` 본문을 읽거나 모델에게 보내서 해결하지 않았다.
- Nest 이메일 변경은 핵심 파일 개수는 같지만, 테스트가 먼저 올라와 nDCG가
  0.4483 → 0.3109로 감소했다. 일부 다른 FastAPI 과제도 순위가 나빠졌다.
- Nest Swagger 헤더·사용자 이메일 충돌 과제는 여전히 정답 파일을 못 찾았다.
- 실제 모델을 실행했던 Nest 파일 mapper 과제의 Recall@5=0, Recall@20=0.5는
  그대로다. 이번 수정으로 그 문제가 해결됐다고 말할 수 없다.

이 20개는 이미 알고 있는 회귀 과제다. 새 과제에 일반화된다는 증거가 아니며,
정답 파일 목록도 모든 의미적 영향 범위를 나타내지 않는다. 새로 만들 파일은
기준 커밋에 없어 애초에 검색할 수 없다. 과제별 가중치나 정답 별칭은 넣지 않았다.

## 큰 입력에서의 계산 비용

별도 Node 프로세스에서 고정된 1만/10만 노드 메타데이터를 시험했다. 아래는
10만 노드의 일반적인 두 단어 검색에서 워밍업 뒤 3회 측정한 중앙값이다.

| 측정값 | 기존 | 변경 후 |
|---|---:|---:|
| 단어 기반 점수 계산 | 4,721.55ms | 2,364.25ms |
| 프로세스 최대 RSS | 815.22MiB | 566.03MiB |

일반 단어 조건에서 가중치와 검색 일치 결과가 전후 같음도 확인했다.
RSS에는 Node와 합성 입력 자체가 포함된다. **모델 실행, 그래프 생성, 전체
PageRank, 테스트, CRUD 구현의 총 시간이 두 배 빨라졌다는 뜻은 아니다.**
원본 수치와 소스 해시는 [성능 기록](artifacts/v28/lexical-performance.json)에 있다.

재현 명령은 다음과 같다. 공개 저장소 미러는 별도로 준비되어 있어야 한다.
첫 명령은 모델 호출·의존성 설치·프로젝트 테스트를 하지 않는다.

```sh
node scripts/benchmark-retrieval-query.mjs --cache /path/to/public-mirrors --output /tmp/new-retrieval-result.json
node scripts/benchmark-lexical-retrieval.mjs
```

## 검증과 남은 목표

- 전체 449개 테스트: **445 PASS, 0 FAIL, 4 SKIP**.
- 전체 커버리지: 줄 90.51%, 분기 80.73%, 함수 98.82%.
  새 검색 모듈은 세 항목 모두 100%지만 이것만으로 실사용 품질을 보증하지 않는다.
- 지정한 결함 16개를 넣는 mutation smoke에서 16개 모두 assertion 실패로 검출했다.
  전체 코드의 mutation score는 아니다. 첫 실험에서 동작이 같아지는 구분자
  변형이 살아남아, 실제 약어 분리를 깨는 변형으로 교체한 과정도 기록했다.
- 설치 패키지 실행, 실제 CLI의 승인 계획 export, 변조·소스 변경 거절, 규칙과
  권한 보존을 검사했다. 공개 Nest 요청을 모델 없이 재생성한 결과, 승인 내용·
  규칙·권한·선택 코드·편집 전 요구 조건이 전후 같고 요청 크기도 18,632바이트로 같다.
- 실제 Windows 2개, 실제 MySQL, 실제 Maven/Gradle 실행은 이번 환경에서
  미실행이다. 회사 코드·운영 DB·기존 프로젝트를 수정하지 않았다.

세부 명령·로그 해시·검증 소스는 [QA 기록](artifacts/v28/qa.json)에 있다.
이 변경은 실패한 큰 후보를 버리고 작은 개선을 반영한 **중간 체크포인트**다.
남은 검색 실패 원인과 선언 정보 부족을 개선하고, 아직 부족한 독립 과제 검사와
실제 Codex/Claude 대조를 이어가야 한다. 3개 백엔드·20개 작업의 전체 완료 시간,
성공률, 규칙 위반, 토큰·비용·재시도 비교라는 최종 목표는 끝나지 않았다.
