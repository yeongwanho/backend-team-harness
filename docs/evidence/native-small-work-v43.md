# 작은 수정의 전체 흐름과 실제 MySQL 검증

이번에는 두 가지를 실제로 확인했습니다. 작은 API 수정은 **BTH와 직접 Codex
모두 구현·검증을 끝냈고**, MySQL 검증에서는 **정상·실패·시간초과를 구분하고
해당 테스트의 컨테이너를 정리했습니다.** 전체 제품 완성이나 일반적인 속도 우위는
아직 주장하지 않습니다.

## 1. 작은 작업에서도 권한 규칙을 지켰는가

과제는 공개 FastAPI 저장소의 `fastapi-05-missing-user`입니다. 관리자가 없는
사용자를 조회하면 404를 반환하되, 일반 사용자의 권한 부족은 계속 403이어야 합니다.
그냥 앞부분에 404 처리를 추가하면 권한 확인 순서가 바뀔 수 있는 작업입니다.

2026-08-31, 고정된 동일 소스에서 `gpt-5.6-sol`, fast/low, provider 총시간
240초로 BTH → 직접 Codex를 순차 실행했습니다. BTH는 최대 3회 호출이 가능했지만
실제 호출은 양쪽 모두 1회였습니다. 후보 코드를 사람이 고쳐 주지 않았습니다.

| 확인 항목 | BTH | 직접 Codex |
| --- | --- | --- |
| 최종 일반 테스트 | 58/58 통과 | 58/58 통과 |
| 독립적인 기능 검증 | 7/7 통과 | 7/7 통과 |
| 작업 중 검증 실행 | 하네스의 소스에 묶인 실행 기록 | 승인 명령의 실패 1회·성공 1회 관찰 |
| 전체 작업 완료 판정 | 확인됨 | 확인됨 |
| 기록된 전체 시간 | 125.364초 | 134.440초 |
| provider 실행 시간 | 62.605초 | 76.896초 |
| 보고된 총 토큰 | 164,740 | 211,087 |
| 캐시 입력 토큰 | 135,680 | 136,704 |
| 미캐시 입력 토큰 | 27,484 | 72,628 |
| 비용 | 미제공 | 미제공 |

이번 한 건에서는 BTH의 시간과 토큰 관찰값이 작았습니다. 하지만 순차 실행 한 번이고,
같은 과제를 과거에도 검토한 환경입니다. 낯선 저장소 전체에 대한 우위나 2배 성능의
증거로 쓰지 않습니다. 전체 시간에는 평가 검증도 들어가며, 직접 CLI 내부의 테스트
시간은 provider 시간에도 포함됩니다. BTH가 외부에서 실행하는 검증 시간과 범위가
다르므로 provider 시간만으로 모델 효율을 단정할 수도 없습니다.

두 후보의 실제 수정은 같았습니다. 권한 검사 **뒤에** 없는 사용자 404 처리를
추가하고 기존 테스트 파일에 회귀 테스트 한 개를 추가했습니다. 수정 전 57개 테스트는
유지됐고, 테스트 삭제·skip·검증 설정 변경은 없었습니다. 독립 검증은 관리자 조회,
본인 조회, 타인 조회 금지, 없는 ID에 대한 일반 사용자의 403, 비로그인 차단,
잘못된 ID 형식까지 확인했습니다. 두 최종 소스는 각각 마지막 검증 기록과 일치합니다.

원본: [실제 쌍대 실행](artifacts/v43/codex-native-small-pair.json).
v42의 미확인 결과를 덮어쓴 것이 아니라 다른 과제의 새 실행입니다. 직접 CLI의
검증 재실행은 관찰했지만 내부 코드 수정 횟수는 여전히 미측정입니다.

### 영향 분석 수치의 한계

BTH가 공급한 코드 문맥의 Recall@5/20과 nDCG@20은 이 과제에서 모두 1.0입니다.
직접 CLI의 관찰된 편집 전 파일 경로로 계산한 값은 모두 0입니다. 그러나 직접 CLI도
정확한 파일을 수정했습니다. 지원하는 명령에서 수집한 경로만 측정한 것이므로
**직접 CLI가 코드를 이해하지 못했다는 뜻이 아닙니다.** 서로 다른 관찰 방식을 같은
의미의 코드 영향 분석 점수로 순위 매기지 않습니다. 이 측정 한계는 남아 있습니다.

## 2. 실제 MySQL에서 무엇을 검증했는가

회사와 무관한 `examples/spring-service`를 임시 Git 저장소에 복사하고 DB Pack을
설치해 실행했습니다. 실제 MySQL 8.4.11에서 Flyway migration을 적용하고
JSON·ENUM·utf8mb4 데이터의 JDBC 저장·조회를 확인했습니다. H2로 대신하지 않았습니다.

| 상황 | BTH 판정 | 소유자 라벨로 확인한 MySQL 컨테이너 잔존 |
| --- | --- | --- |
| 정상 migration·조회 | 성공 | 0 |
| DB 작업 후 assertion 실패 | 실패 | 0 |
| 테스트 JVM 강제 종료 | 실패 | 0 |
| 허용 시간 초과 | 시간초과 실패 | 0 |

실제 통합 검사 1개 안에서 위 4개 시나리오가 모두 통과했고, 총 약 128초가 걸렸습니다.
이는 DB Pack 예제의 증거입니다. 20개 과제 중 MySQL 관련 과제를 모델이 구현했다거나
회사 migration·락·트랜잭션 전체가 검증됐다는 뜻은 아닙니다.

### 실행 전에 고친 정리 위험

기존 테스트는 같은 MySQL 이미지로 새로 생긴 컨테이너를 정리 대상으로 잡았습니다.
동시에 다른 개발자가 같은 이미지를 실행하면 혼동할 수 있어 아래처럼 바꿨습니다.

- 실행마다 고유 소유자 UUID 라벨을 부여합니다.
- 정리 전 전체 컨테이너 ID·소유자 라벨·예상 이미지 ID를 모두 확인합니다.
- 다른 소유자, 다른 이미지, 잘못된 ID, Docker 조회 실패 시 삭제하지 않습니다.
- DB 파일은 크기가 제한된 메모리 임시 저장소를 쓰고, 비밀번호는 무작위로 만듭니다.
- 포트는 로컬 루프백 주소에만 동적으로 열며 실제 바인딩도 테스트에서 확인합니다.
- MySQL 이미지는 이미 내려받은 것을 사용하며 테스트가 암묵적으로 새 이미지를 받지 않습니다.

다른 컨테이너를 잘못 선택하는 경계는 대역 테스트로도 검증했습니다. 실제 두 개발자가
동시에 쓰는 협업 시험은 별도입니다. Gradle·컨테이너의 외부 통신을 운영체제에서
차단하는 기능이 생긴 것도 아닙니다.

## 3. 20개 과제는 어디까지 왔는가

‘기능 검증 준비’는 수정 전 실패·정답 코드 통과의 대조 근거가 현재 검증 설정과
맞는다는 뜻입니다. **AI가 해당 작업을 완수했다는 뜻이 아닙니다.** 과거 실행은
서로 다른 코드와 비교 방식이 섞여 있어 현재 제품의 성공률로 합산하지 않습니다.

| 과제 | 기능 검증 준비 | 과거 BTH/direct 실제 실행 | native 전체 흐름 쌍대 완료 |
| --- | --- | --- | --- |
| Spring 반려동물 연결 | 확인 | 있음 | 미실행 |
| Spring 이름 공백 검색 | 확인 | 있음 | 미실행 |
| Spring 이름 중복 제약 | 미설정 | 없음 | 미실행 |
| Spring 방문 날짜 검증 | 확인 | 있음 | 미실행 |
| Spring ID 바인딩 보호 | 확인 | 있음 | 미실행 |
| Spring 반려동물 수정 | 확인 | 있음 | 미실행 |
| Spring MySQL 사용자 | 미설정 | 없음 | 미실행 |
| Nest 세션 해시 갱신 | 설정됨·대조 미확인 | 없음 | 미실행 |

native 쌍대 시도 2개·완료 확인 1개입니다. [기계로 대조한 전체 현황](artifacts/v43/corpus-ledger.json)은
v42의 원본 성공 표기를 그대로 믿지 않고 미확인 검증을 별도로 재판정합니다.

## 4. 회귀 검사와 다음 조건

- 전체 회귀 614개: **610 통과, 실패 0, 4 skip**. MySQL은 기본 실행에서는 opt-in이라 건너뛰지만 이번 별도 실제 실행은 통과했습니다. 실제 Windows 2개와 별도 Maven/Gradle 통합 검사는 이번에 실행하지 않았습니다.
- 코드 커버리지: 줄 91.45%, 분기 83.20%, 함수 98.72%. 결함이 없다는 보증은 아닙니다.
- 선별한 의도적 결함 48개를 모두 실제 assertion 실패로 탐지했습니다. 소유자 라벨·이미지 검사 무력화도 포함하며 전체 가능한 변이에 대한 검사는 아닙니다.
- 설치한 패키지의 실행 검사와 구문 검사가 통과했습니다. 공개 전 원본 실행·최종 코드·집계의 지문을 대조했습니다.

전체 목표는 계속 진행 중입니다. 남은 과제의 독립 검증과 세 백엔드의 native 실행,
실제 Claude native 흐름, 비교 가능한 영향 분석 측정, 회사 기획·규칙의 이해,
Windows 실기와 두 개발자 인수인계·적용 검증을 아직 완료로 볼 수 없습니다.
준비된 기획 결정과 환경에서 끝난 이번 결과가 이 조건들을 대신하지는 않습니다.

재현 명령과 소스·로그 지문은 [QA 기록](artifacts/v43/qa.json)에 남깁니다.
실제 DB 테스트는 캐시된 검토 이미지와 Docker가 있는 환경에서 명시적으로 실행합니다.

```bash
BTH_REAL_DB_E2E=1 node --test test/db-real-e2e.test.mjs
```

회사 원본, 운영 DB, 사용자 설정은 변경하지 않았습니다. 공개 FastAPI 후보는
감사용으로 보존했고 실제 프로젝트에 적용하지 않았습니다.
