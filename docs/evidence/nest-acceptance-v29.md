# 테스트를 작성했는데 왜 한 개도 실행되지 않았나

이번에는 공개 NestJS 저장소에 독립 검사를 추가하고, 이메일 충돌 수정 과제를
실제 Codex에 맡겼다. **첫 비교는 하네스와 단독 실행 모두 실패했다.**
그 과정에서 찾은 테스트 위치 안내 문제를 보완했지만, 재실행도 생성된 테스트의
컴파일 오류로 실패했다. 전체 하네스가 완성됐거나 효율이 좋아졌다는 결과가 아니다.

## 독립 검사는 두 과제를 더 확인했다

모델이 자기 테스트만 통과하고 끝나지 않도록, 따로 보관한 검사로 실제 원본과
정답 커밋을 실행했다. 검사 파일은 모델의 작업 폴더에 넣지 않는다. 검사마다
파일 해시와 실행돼야 할 테스트 이름을 고정했다.

| 과제 | 원본 코드 | 정답 코드 | 판정 |
|---|---|---|---|
| 사용자의 이메일 중복 확인 | 3개 실패·4개 통과 | 7개 통과 | 새로 확인 |
| Swagger 언어 헤더 | 3개 실패 | 3개 통과 | 새로 확인 |
| 기존 파일 mapper·interceptor | 3개 실패·4개 통과 | 7개 통과 | 기존 검사 유지 |
| 세션 ID·hash 조건부 변경 | 의존성 설치 실패 | 의존성 설치 실패 | 미검증 |

이로써 기존 Spring 5개·Nest 1개에 Nest 2개가 더해져, 알려진 20개 과제 중
**독립 검사를 확인한 것은 8개**다. 설정이 있는 것과 실행 검증이 끝난 것은 다르다.
세션용 12개 검사는 작성했지만 아직 컴파일·실행을 확인하지 못했다.
[최종 고정 설정으로 다시 실행한 대조 기록](artifacts/v29/final-controls.json).

이메일 검사는 실제 UsersService를 실행하되 저장소와 파일 조회는 대역을 사용한다.
Swagger는 실제 bootstrap·Nest·Swagger 문서 생성을 실행하되, 앱 모듈은 작은
시험용 모듈이고 listen은 가로챈다. 운영 DB, 실제 HTTP 배포, DB 경합 안전성을
증명한 검사가 아니다.

처음의 실패도 남겼다. 이메일·Swagger는 오프라인 의존성 캐시가 비어 있었다.
검토한 공개 lockfile로 임시 clone의 캐시만 준비하고, 같은 검사를 오프라인으로
다시 실행했다. Swagger 검사 자체에도 Nest의 proxy 메서드를 잘못 대체한 문제가
있었다. 원본과 정답이 모두 실패했으므로 유효한 대조군으로 세지 않았고, 수정한
검사를 별도 해시로 재검증했다. [실패와 재검증 이력](artifacts/v29/control-history.json).

세션 과제는 고정된 lockfile에 필요한 `gcp-metadata@7.0.1` 항목이 없어 `npm ci`가
거절됐다. 기존 npm 10.1.0과 별도로 임시 설치한 10.9.9에서 같은 문제가 났다.
원본 lockfile을 임의 수정하거나 peer 의존성 검사를 끄지 않았다. 전역 npm과
인증 설정도 바꾸지 않았다.

재현하려면 공개 미러와 승인된 의존성 캐시를 준비한 뒤 실행한다. 아래 명령은
모델 호출 없이 원본·정답 대조만 하며, 기존 결과 파일은 덮어쓰지 않는다.

```sh
node scripts/acceptance-controls.mjs --cache /path/to/public-mirrors --output /tmp/new-controls.json --task nest-06-user-email-conflict --task nest-03-swagger-language-header
```

## 실제 첫 비교: 양쪽 모두 실패

같은 요구사항·모델 `gpt-5.6-sol`·빠른 모드로 각 한 번씩 실행했다.
정답 커밋과 기존 Git 이력을 제거한 각각의 임시 프로젝트를 사용했다.

| 첫 시도 | 하네스 | 직접 Codex |
|---|---:|---:|
| 구현 흐름 시간 | 103.4초 | 65.5초 |
| 총 토큰 — 캐시 입력 포함 | 304,296 | 194,346 |
| 캐시 제외 입력 토큰 | 36,959 | 34,733 |
| 최종 검사에서 실행된 테스트 | 0 | 0 |
| 작업 성공 | 실패 | 실패 |

둘 다 `src/users/users.service.ts`와 `test/admin/users.e2e-spec.ts`를 수정했다.
그런데 기본 `test` 명령은 `src` 안의 `*.spec.ts`만 읽는다. E2E 테스트는 별도
명령의 대상이다. **기존 테스트를 참고한다는 것만으로는 충분하지 않았다.**

시간은 각 구현 흐름 시작부터 필수 검증까지이며, 독립 검사와 비교 환경 준비
시간은 별도다. 하네스의 격리 의존성 준비는 흐름 시간에 포함된다. 총 준비 포함
시간도 원본 기록에 있다. 토큰은 provider가 보고한 값이며 달러 비용은 제공되지
않아 `null`로 남겼다. 이 한 번의 순차 비교에서는 하네스 우위를 확인하지 못했다.
[첫 비교 전체 기록](artifacts/v29/initial-codex-pair.json).

## 보완한 부분

하네스가 생성한 Jest 검사 명령과 실행 파일이 실제 설정과 일치하는지 확인한 뒤,
`package.json`의 테스트 위치·이름 규칙을 구현 요청에 붙인다. 파일·검사 설정의
해시를 함께 기록하고, 인접 E2E 테스트를 무작정 따라 쓰지 않도록 설명한다.

별도 검사 명령, 추가 CLI 옵션, 외부·동적 설정, preset, 여러 project, 안전하지
않은 파일은 추측해서 해석하지 않는다. 그런 경우 `unknown`으로 남겨 직접
확인하게 한다. 현재는 **정확히 인식한 기본 Jest 검사와 inline 설정**에 한정된
작성 안내이지, 모든 프레임워크의 테스트 설정을 해석하는 기능이 아니다.

추가 모델 호출이나 저장소 전체 탐색 없이 이미 선언된 입력만 한 번 읽는다.
승인·쓰기 범위·테스트 최소 실행 수·전체 필수 검사는 바꾸지 않았다. 실제 공개
원본을 모델 없이 재생성했을 때 `rootDir: src`와 이름 규칙을 정확히 전달했다.
[원본 설정 재생 결과](artifacts/v29/test-authoring-replay.json).

## 보완 후 실행에서도 남은 실패

새 프로토콜 `test-authoring-v29`로 같은 모델·빠른 모드의 하네스 실행을 한 번
더 했다. 앞선 실패를 대체하는 표본이 아니라 **개선 확인용 후속 실행**이다.

이번에는 `src/users/users.service.spec.ts`에 테스트를 작성했다. 하지만 공개 타입
`Partial<HttpException>`에 없는 `response` 필드를 검사해 `TS2353` 컴파일 오류가
났다. 실행 테스트는 여전히 0개였고 최종 판정은 실패였다. 96.0초·303,701토큰을
사용했다. 검사 위치 문제는 보완됐지만 이 과제를 끝냈다고 말할 수 없다.

현재 자동 복구 입력에는 `junit_reports_missing` 같은 요약만 남고, 이 컴파일
오류 코드와 위치는 빠져 있었다. 실패 원인을 안전하게 전달하는 기능이 더
필요하다는 실제 근거다. 실패 후보와 기록은 조사용 소유 worktree에 보존했고,
회사 코드나 원본 프로젝트에 적용하지 않았다.
[후속 실패·소스 해시·실제 검사 재실행 진단](artifacts/v29/codex-authoring-followup.json).

첫 비교와 후속 실행을 합쳐 이번 모델 호출은 3번이다. 불리한 결과를 버리고
통과할 때까지 실행한 뒤 성공률로 발표하지 않는다. 하네스가 처음 제공한 파일
목록의 이 과제 Recall은 여전히 0이며, 모델이 추가로 찾아 수정한 것과 구분한다.

## 남은 검증

실제 Codex를 실행한 서로 다른 과제는 이제 4개지만, 20개 전체의 Codex·Claude
짝 비교는 끝나지 않았다. 이번에는 Claude 실행·실제 Windows·MySQL·JVM 검증을
추가하지 않았다. 세션 의존성 문제, 나머지 독립 검사, 컴파일 진단 전달, 일반화된
파일 검색과 효율 개선이 남아 있다. 문서 생성기 과제도 원본의 ‘없으면 예외’와
일부 저장소의 ‘없으면 null’ 동작이 달라, 한 가지 반환 규칙으로 뭉뚱그리지 않는다.

이번 패치의 로컬 회귀 검증과 생략 사항은 [QA 기록](artifacts/v29/qa.json)에 남긴다.
전체 458개 중 454개 통과·0개 실패·4개 생략이며, 커버리지는 줄 90.56%·분기
80.89%·함수 98.83%다. 선택한 결함 18개를 주입하는 mutation smoke는 모두
assertion 실패로 검출했고, 임시 설치한 0.9.0 패키지의 CLI 버전 실행도 통과했다.
이 수치는 생성된 회사 코드나 모든 실제 provider 작업의 성공률이 아니다.
이 변경은 검증 범위를 늘리고 실제 실패 하나의 원인을 줄인 중간 체크포인트다.
