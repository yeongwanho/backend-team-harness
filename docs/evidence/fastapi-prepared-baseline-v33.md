# 첫 FastAPI 실제 비교: 둘 다 정답, 아직 하네스가 더 느리다

목표는 기능 수를 늘리는 것이 아니다. **새 백엔드에서도 프로젝트 규칙을 지키며
실제 구현을 빠르고 안전하게 끝내는 것**이다. 작은 작업에서는 준비와 문서가
구현보다 무거워지지 않아야 한다. 이번에는 이 목표를 공개 FastAPI의 실제 수정
한 건으로 비교했다. 전체 3개 백엔드·20개 과제 목표는 아직 미완료다.

## 실제로 시킨 일과 결과

공개 `fastapi/full-stack-fastapi-template`의
`fe3bafc6f6732698ed2c58424f64065a4209ad47`에서 다음 요구사항을 각각 실행했다.

> 관리자가 없는 사용자를 조회하면 404를 돌려준다. 일반 사용자의 권한 거부와
> 기존 사용자 조회는 그대로 유지하고, 회귀 테스트를 추가한다.

같은 Codex CLI 0.151.0, `gpt-5.6-sol`, 빠른 모드, 최대 시도 1회였다.
모델은 코드와 테스트를 편집하고, 테스트 실행은 공통 검증기가 담당했다.

**이번 작은 작업에서는 BTH가 약 15초 더 걸렸다.** 총 토큰도 약 2.12배였다.
다만 캐시된 입력을 모두 새 입력 비용처럼 계산하면 안 된다. 캐시를 뺀 입력은
약 11% 더 많았다. 실제 USD 비용은 관찰되지 않아 추정값으로 채우지 않았다.

두 후보의 실제 코드도 직접 대조했다. 둘 다 기존 403 권한 검사 뒤에 404를
추가했으며, 없는 사용자에 대한 응답 코드와 본문을 확인하는 테스트를 작성했다.
독립 검사는 일반 사용자의 자기 조회·타인 조회·없는 ID, 비로그인 접근,
잘못된 ID 형식까지 확인했다. 원래 코드에서는 목표 회귀가 실패하고, 정답 코드와
두 후보에서는 모두 통과했다. [원본 결과와 실행 근거](artifacts/v33/codex-pair.json).

한 번의 관찰로 평균 성능이나 인과관계를 확정할 수는 없다. BTH의 요청 파일은
18,210바이트, 직접 실행 프롬프트는 2,366바이트였다. 다음 최적화 후보는 작은
작업의 중복 문서와 입력이다. 같은 검증을 유지하면서 이것을 줄여 다시 측정해야
한다. 이번 결과를 속도 향상이나 “두 배 좋은 하네스”의 근거로 쓰지 않는다.
이미 의존성이 캐시된 한 PC에서 BTH 다음 직접 실행 순서로 측정했다. 순서를
무작위화한 반복 실험이나 전용 성능 측정 환경이 아니므로 순서·캐시 효과도 남는다.

## 왜 테스트 준비부터 고쳤나

v32에서는 원래 테스트 55개 중 52개만 통과했다. 이를 모델에게 고치게 하면
요구사항 구현 능력 대신 테스트 환경 정비 능력을 비교하게 된다.

그래서 평가 전용 공통 준비를 두 비교군에 똑같이 적용했다.

- DB 연결 준비 테스트 2개의 잘못된 mock 대상과 assertion을 바로잡았다.
- 이메일은 실제 MIME 조립과 애플리케이션 호출을 유지하되 외부 전송만 메모리
  안에서 처리했다. 테스트 이메일은 예약된 `example.com` 주소로 제한했다.
- 메일 환경 자체를 확인하는 테스트 2개를 추가했다.
- 실제 PostgreSQL 16 임시 컨테이너와 오프라인 Python 준비를 사용했다.

첫 보정에서는 57개 중 56개가 통과했다. 남은 실패는 원래 테스트 도우미가
임의의 `.com` 도메인을 만들었기 때문이었다. 안전 제한을 풀지 않고 도우미를
예약 도메인으로 고정한 뒤 57/57을 확인했다. 새 임시 clone에서 공통 준비
절차를 실행해도 같은 결과였다. [준비·대조 검증](artifacts/v33/preflight.json).

**원래 55개 테스트를 제외하지 않았다.** 최종 JUnit의 테스트 이름을 원래 결과와
대조해 모두 남아 있음을 확인했다. 다만 위 두 테스트 본문과 이메일 도우미는
명시적으로 보정했으므로 “원본 테스트를 한 글자도 바꾸지 않았다”는 뜻은 아니다.
보정 전후 해시를 고정했고, 대상 파일이 다르면 적용을 거부한다.

이 보정은 공개 평가 프로젝트에만 적용된다. 회사 테스트를 자동으로 고쳐서
통과시키는 일반 기능이 아니다. 실제 SMTP 전달이나 Alembic migration 안전성도
검증한 것이 아니다. PostgreSQL 사용은 이 공개 프로젝트의 요구사항이며,
제품의 MySQL 우선 방향을 바꾼 것이 아니다.

## 검증기를 바꿔서 통과하지 못하게 하기

공통 준비는 테스트 파일·검증 실행기만 수정할 수 있다. 경로 이탈, symlink,
해시 불일치, 잘못된 UTF-8과 크기 제한을 검사한다. 파일은 완성된 바이트로
교체하며 실패 시 자기 변경을 복구한다. 복구 중 다른 변경을 발견하면 덮어쓰지
않는다. 여러 파일 전체를 하나의 원자적 파일시스템 트랜잭션으로 보장하지는 않는다.

준비 파일은 필수 검증 입력으로 묶었다. 직접 실행도 실제 바이트를 다시 읽어서
비교한다. 검수 중, 추가 파일뿐 아니라 **그 실행기가 참조하는 생성 파일과
빌드 설정**도 보호해야 한다는 빈틈을 재현했다. Git의 `assume-unchanged`로 변경을
숨긴 테스트가 수정 전에는 잘못 통과했고, 보강 후에는 실패 판정됐다. 검증 실행
전후 모두 검사하고, 입력이 없으면 모델을 호출하지 않는다.

실제 비교 프로세스는 이 마지막 보강 전에 이미 시작돼 있었다. 따라서 보강이
실측 당시 실행됐다고 소급하지 않는다. 대신 두 후보의 모든 검증 입력을 당시
기준선에 기록된 해시와 다시 비교해 변경이 없음을 확인했다. Git 저장 바이트는
줄바꿈 정규화가 있으므로 당시 실행 바이트의 해시를 기준으로 삼았다.
[두 비교군 입력 일치·원래 테스트 보존 근거](artifacts/v33/integrity.json).

- 커버리지: 줄 **90.96%**, 분기 **82.14%**, 함수 **98.90%**.

- 문법, 설치된 패키지 실행, fixture 해시 및 CLI 문서 계약 통과.
- 운영 의존성 감사에서 보고된 취약점 0개. 무결점 보장은 아니다.

명령·로그 해시·실패 재현과 생략 범위는 [QA 근거](artifacts/v33/qa.json)에 있다.
실제 Windows provider/하위 프로세스 종료, 별도 opt-in MySQL/JVM 실행은 이번에
하지 않았다. Python socket 제한과 Docker loopback 포트는 완전한 OS egress
격리가 아니다. 회사 정보·운영 DB·실제 메일 주소는 사용하지 않았다.

이번 비교로 실제 모델을 실행한 과제는 기존 4개에서 5개가 됐다. 이것을 전체
완성률 25%로 환산하지 않는다. 독립 대조가 준비된 10/20 범위가 늘어난 것도
아니다. 나머지 과제, Claude 교차 비교, 반복 측정, 작은 작업의 입력·시간 개선이
남아 있다. 정식 npm 버전 발행이나 전체 목표 완료도 아니다.

Codex 실행 방식은 [공식 비대화형 실행 문서](https://learn.chatgpt.com/docs/non-interactive-mode)와
설치된 CLI 도움말로 확인했다. 공개 프로젝트에서 가져온 테스트 도우미의 라이선스는
[third-party notices](../../THIRD_PARTY_NOTICES.md)에 보존했다.
