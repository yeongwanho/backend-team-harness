# 기본 검사는 통과했지만, 다른 소유자의 데이터를 바꾸는 후보를 찾았다

목표는 기능 목록을 늘리는 것이 아니라, 새 백엔드에서도 규칙을 지키며 실제
수정을 마치고 증거를 남기는 것이다. 이번에는 같은 쉬운 과제를 반복하지 않고
ID 변조 방어·기존 데이터 수정의 실제 구현을 비교하고 방문 날짜 검사의 편향을
검토했다. **현재 하네스를 완성·안전한 구현기로 판정할 수 없다.** BTH가 만든
데이터 수정 후보는 원래 검사에 통과했지만, 추가 확인에서 소유권 회귀가 재현됐다.

## ID 변조 방어: BTH 통과, 직접 실행은 포맷 검사에서 중단

폼으로 소유자·반려동물·방문 기록의 ID를 바꾸지 못하게 하되, 이름·날짜 같은
정상 입력과 기존 유효성 검사는 유지하는 과제다. 동일한 공개 원본·Codex
`gpt-5.6-sol`·빠른 모드·최대 1회 시도, BTH → 직접 실행 순서다.

| 항목 | BTH | 직접 Codex |
|---|---:|---:|
| 첫 시도 전체 검증 | 통과 | 실패 |
| 일반 테스트 | 63/63 | 실행 전 중단 |
| 별도 요구사항 동작 검사 | 5/5 | 후보 검사 미실행 |
| 구현 + 일반 검증 | 162.06초 | 124.95초 |
| 모델 실행 | 101.44초 | 121.76초 |
| 준비·대조 검사까지 포함 | 342.05초 | 253.56초 |
| 입력 / 캐시 입력 | 252,398 / 209,152 | 222,744 / 182,528 |
| 캐시 제외 입력 / 출력 | 43,246 / 3,737 | 40,216 / 4,614 |
| 총 토큰 | 256,135 | 227,358 |
| 실제 USD 비용 | 확인 불가 | 확인 불가 |

두 후보의 방어 코드는 같았다. 세 컨트롤러에서 직접 ID와 중첩 ID 입력을 막고
기존 PetValidator를 유지했다. BTH는 원래 59개 테스트를 모두 실행하고 4개를
추가했다. 독립 검사는 실제 HTTP 바인딩으로 ID 보존과 정상 입력·검증 유지를
확인했다. [실행 원본·소스 및 테스트 해시](artifacts/v35/binder-pair.json).

하지만 **BTH가 추가한 4개 테스트는 설정 배열과 validator 종류를 확인하는
수준**이다. 직접 Codex는 HTTP 요청과 저장 인자를 확인하는 테스트를 작성했지만,
3개 테스트 파일의 Spring JavaFormat 규칙 위반으로 실행조차 못 했다. 첫 시도
결과는 그대로 실패로 보존했고, 후보 코드를 고쳐 성공으로 바꾸지 않았다.
추가 `mvnw -q -o validate`로 같은 실패를 재현했다.
[실패 원인과 해당 파일](artifacts/v35/binder-direct-diagnosis.json).

따라서 “BTH가 이번에 통과했다”와 “BTH가 더 좋은 테스트를 만들었다”는 다른
주장이다. 후자는 증명하지 못했다. 포맷에서 중단된 직접 실행은 전체 검증 시간이
짧을 수밖에 없으므로, 위 시간으로 속도 우위를 계산하지 않는다. BTH 실행 일부는
평가 테스트의 포맷 준비 검사와 겹쳤고, 반복 측정·전용 성능 환경도 아니다.

### 자동 위반 집계의 빈틈

직접 실행 기록의 `ruleViolations`는 빈 배열, `executionDiagnostics`는 null이었다.
실제로는 포맷 규칙 위반이 3개 파일에 있었다. 현재 지표는 변경 범위·보호 입력
같은 계약 위반을 세는 것이지 프로젝트의 모든 규칙을 검사했다는 뜻이 아니다.
따라서 이를 “프로젝트 규칙 위반 0건”으로 표시하면 잘못이다. 포맷 오류의 구조화된
진단과 후속 복구 연결은 남은 개선 항목으로 유지한다.

## 기존 데이터 수정: 처음에는 통과했지만 적용하면 안 되는 후보

BTH는 58개 일반 테스트와 사전 정의한 4개 JPA/H2 검사를 첫 시도에 통과했다.
원래 56개 테스트를 보존하고 2개를 추가했으며, 수정·중복 방지·신규 객체 처리·
오류 입력 보존을 검사했다. [기존 기준의 원본 실행 기록](artifacts/v35/pet-pair.json).

그런데 diff를 읽으니 `Owner.updatePet()`를 새로 만들고, 대상 소유자에게 없는
ID도 목록에 추가했다. 원래 `addPet()`에는 새 객체일 때만 추가하는 조건이 있었는데
그 조건을 우회한 것이다. 컨트롤러도 소유자에게 없는 ID에 새 객체를 만들어 줬다.

이를 별도 임시 복사본과 실제 JPA/H2 행으로 확인했다. 소유자 1의 수정 요청에
소유자 2의 기존 pet ID를 넣었을 때:

| 소스 | 추가 소유권 검사 결과 |
|---|---|
| 고정 원본 | 다른 소유자의 행 유지 |
| 기준 수정본 | 다른 소유자의 행 유지 |
| BTH 후보 | **`pets.owner_id`가 2 → 1로 변경됨** |
| 직접 Codex 후보 | 테스트 파일 포맷 위반으로 검사 전 중단 |

이것은 추측이 아니라 `flush()` 후 다시 읽은 값의 비교다. 다만 테스트가 호출한
표면은 컨트롤러/JPA이며, 실제 HTTP 인증·운영 DB 침해를 실증했다는 뜻은 아니다.
모든 데이터는 임시 H2에서 트랜잭션 롤백됐고 회사 저장소나 DB는 건드리지 않았다.
[검사·소스 해시·관측값](artifacts/v35/pet-ownership-audit.json).

처음 추가 검사에서는 합성 이름이 컬럼 길이를 넘어서 DB 오류가 먼저 났다.
그 결과를 소유권 변경의 증거로 쓰지 않고, 유효한 길이로 바꾼 새 검사에서 재현했다.
[제외한 초기 검사](artifacts/v35/pet-ownership-invalid-input.json).

사전 정의한 첫 시도 점수는 소급해서 지우지 않는다. 하지만 **그 후보의 적용
가능 여부는 거절**이다. 다음 버전의 독립 검사는 이 회귀까지 포함한 5개 검사로
강화했다. 이는 이번에 발견한 사례를 학습한 회귀 방지이지, 처음부터 찾아냈다는
주장이 아니다. 구현기가 이 경계를 자동으로 보존하도록 만드는 작업은 남아 있다.

강화한 통합 검사도 실제로 실행했다. 원본은 기존 수정 버그로 실패했고 기준
수정본은 5개 모두 통과했다. 보존된 BTH 후보는 원래 4개를 통과하고 새 소유권
검사만 실패했다. [다음 버전 검사로 재판정한 근거](artifacts/v35/pet-strengthened-acceptance.json).

## 방문 날짜 평가 기준의 편향을 먼저 수정

기존 독립 검사는 요구사항에 없는 특정 오류 키 `typeMismatch.visitDate`와
8개 properties 파일 수정을 요구했다. 동작이 맞아도 Bean Validation이나 다른
메시지 키를 쓰면 실패할 수 있었다. 모델에게 정답 구현 방식을 알려주는 대신,
실제 폼의 날짜 오류·내일 기본값·최소 날짜·영어/독일어 오류 렌더링을 검사하도록
수정했다. 빈 설명 거절과 내일 이후 날짜 허용은 유지한다.

초기 평가 테스트 자체의 포맷 위반도 발견했다. 이 단계는 기능 회귀 재현이나
구현 실패로 세지 않고 별도 준비 실패로 남겼다.
[실패 당시 검사와 해시](artifacts/v35/visit-oracle-format-failure.json).

검증 범위는 정상 원본/수정본 대조뿐 아니라, 메시지 키를 바꾼 동일 동작,
`@Future` 대체 구현, 독일어 메시지를 영어로 되돌린 오류 구현까지 포함한다.
이 결과를 확인하기 전에는 수정된 평가 기준으로 모델을 실행하지 않는다.

실제 Maven 대조 결과는 원본의 회귀 실패, 기준 수정본 통과, 메시지 키 변경
통과, `@Future` 대안 통과, 독일어 메시지를 영어로 되돌린 후보 실패였다.
두 언어의 실제 오류 렌더링을 검사하며, 모든 언어의 번역 품질을 보증하지는 않는다.
[대체 구현 및 부정 대조 결과](artifacts/v35/visit-oracle-variants.json).

검사 도중 디스크 부족으로 한 실행이 중단됐다. 약 766MB인 공개 Git 미러를
여러 임시 복사본에 남겨둔 것이 부담이었다. 이제 완료된 합성 대안의 임시
복사본은 바로 정리하고, 뒤의 준비가 실패해도 앞의 완료 결과를 JSON으로
남긴다. 사용자 파일·공용 캐시·기존 후보 증거는 삭제하지 않았다. 이 변경 후
세 대안을 모두 재검증했다. 실제 방문 날짜 **모델 구현 비교는 아직 안 했다**.
새로 발견한 소유권 회귀를 우선 처리하기 위해 미뤘다.

## 무엇이 개선됐고, 무엇이 남았나

이번에 개선한 것은 **평가의 공정성·회귀 검출·증거 보존**이다. 일반 사용자의
모든 프로젝트에서 소유권을 자동으로 보호하도록 구현기를 고쳤다는 뜻은 아니다.
기존 BTH 후보도 적용하지 않았다. `successAt1` 한 칸만 보고 완료를 선언하면
놓칠 수 있는 사례를 확보했다.

다음 구현 우선순위는 다음과 같다.

1. 기존 소유권·관계 변경 제한을 보존하는지 판단하고, 증거가 없으면 적용 후보를
   준비 완료로 표시하지 않기. 이번 회귀를 실제 자동 구현·복구 흐름에서도 막아야 한다.
2. Spring JavaFormat 같은 테스트 실행 전 오류를 안전한 코드·파일 경로로 전달해
   일반적인 “테스트 보고서 없음”으로 끝나지 않게 하기.
3. 실제 동작을 확인하는 테스트와 설정값만 확인하는 테스트를 구분하고, 소유권·
   관계 변경 같은 위험한 수정에만 추가 검증 비용을 쓰기.
4. 남은 공개 과제와 Claude 비교를 계속 수행하기. 현재 관찰을 속도 우위나 전체
   프로젝트 안전성으로 일반화하지 않기.

## 20개 과제의 현재 위치

“대조 완료”는 원본과 기준 수정본으로 **검사 자체를 검증했다**는 뜻이고,
“양쪽 실행”은 실제 BTH/직접 모델 구현을 둘 다 관찰했다는 뜻이다.

이번 변경 범위의 Node 검사는 45/45 통과했고 구문 검사도 통과했다. 실행부
런타임 소스는 이번에 변경하지 않았다. 전체 회귀·커버리지·변이 검사를 새로
돌렸다고 주장하지 않으며, 실제 Windows·Claude 재비교·20개 과제 완주는 남아 있다.
MySQL 일반화·운영 환경 보장·자동 구현의 소유권 보존도 이번 결과로 입증되지 않는다.
