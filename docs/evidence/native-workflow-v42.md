# v42 — 구현부터 테스트·수정까지 같은 작업 요청으로 비교하기

이전 비교는 AI에게 테스트를 실행하지 말라고 지시했습니다. 코드를 작성하는 능력은
볼 수 있지만, 실제로 쓰려는 하네스의 전체 작업 흐름을 평가하기에는 부족했습니다.
이번에는 기존 결과를 덮어쓰지 않고 별도 비교 모드를 만들었습니다.

## 달라진 비교 방법

| 항목 | 기존 controlled-edit | 새 native-workflow |
| --- | --- | --- |
| 직접 CLI | 한 번 코드·테스트 작성 | 한 세션에서 구현·검증 명령 실행·실패 수정 |
| BTH | 한 번 구현 후 검증 | 기존 계획·격리 구현·검증·최대 3회 호출 복구 |
| 성공@1 | 한 모델 호출의 성공 | 한 전체 작업 요청의 성공 |
| 호출 시간 예산 | 호출별 제한 | 경로별 provider 호출 시간 합계 제한 |
| 최종 판정 | 구조화 검증 + 독립 과제 검사 | 동일하게 별도 평가기가 판정 |

직접 CLI에 요구한 검증 명령은 공개 테스트 환경에 고정된 명령뿐입니다. 모델이
테스트 성공을 말해도 평가기가 다시 검사합니다. 테스트 도우미와 검증 설정을
바꾸거나 허용 범위 밖 파일을 변경한 것이 확인되면 실패입니다. 일반 `bth work`의 모델 실행 권한은
확장하지 않았습니다. Claude의 Bash 추가는 이 비교의 명시적 직접 실행에만
적용됩니다. 기본 모델 도구에는 여전히 Bash를 넣지 않습니다.

명령 승인 규칙은 쉘 권한을 전면 해제하는 옵션이 아닙니다. 다만 CLI의 승인 기능이
운영체제 수준 네트워크 격리를 뜻하지도 않습니다. 명령별 승인 기능의 의미는
[Claude 공식 CLI 문서](https://code.claude.com/docs/en/cli-usage)와 로컬 `claude --help`를
대조했습니다. 공개 합성 테스트 환경만 실행하며 회사·운영 DB를 대상으로 하지 않습니다.

## 시간·비용·재시도를 읽는 방법

native 시간은 준비된 작업공간에서 시작하여 구현·하네스 준비·검증·독립 수락 검사까지
포함합니다. 공통 의존성 설치와 수정 전/정답 대조군 준비는 별도 `totalElapsedMs`에
들어갑니다. 그래서 v41의 편집+일반 검증 시간과 그대로 비교하면 안 됩니다.

두 경로에 같은 provider 시간 총예산을 줍니다. 하네스가 두 번째 모델을 부르면
첫 호출에서 실제로 쓴 시간을 뺀 나머지만 전달합니다. 검증·수락 검사 시간은 이
모델 예산에 포함하지 않습니다. Claude의 비용도 누적 보고값으로 남은 상한을
전달하며 비용이 사라지면 추가 호출하지 않습니다. Codex의 달러 상한은 지원하지
않고, 비용 미제공은 0달러가 아닙니다. 모델 프로세스 종료 유예 등 실제 초과 가능성은
기록된 시간으로 확인해야 합니다.

직접 CLI가 자기 세션 안에서 실행한 테스트 시간은 그 provider 시간에 포함됩니다.
BTH가 밖에서 실행한 검증 시간은 포함되지 않습니다. 따라서 같은 240초 상한은
동일한 전체 작업 시간이나 동일한 모델 사고 시간을 보장하지 않습니다. 효율 판단에는
별도로 기록한 전체 시간과 실제 사용량이 필요합니다.

`providerInvocations`는 실제 모델 호출 수입니다. BTH의 추가 호출 수는 알 수 있지만
직접 CLI가 내부에서 몇 번 고쳤는지는 아직 정확히 세지 못합니다. 그 재시도율은
미측정으로 남깁니다. 이 한계를 감춘 채 두 경로의 재시도율을 비교하지 않습니다.
결과를 재사용할 때 모드·모델·소스뿐 아니라 시간·비용·복구 상한도 대조합니다.

## 실제로 확인한 결과

**코드는 양쪽 모두 통과했지만, 완료된 전체 흐름 비교를 확보한 것은 아닙니다.**
직접 CLI가 자기 검증 명령을 실행했는지 관찰하지 못했기 때문입니다.

2026-08-31 공개 FastAPI 저장소의 로그인·비밀번호 복구 과제
`fastapi-04-constant-time-login`을 BTH → 직접 Codex 순서로 한 번씩 실행했습니다.
같은 고정 소스·요구사항·검증 환경, `gpt-5.6-sol`, high effort,
provider 총시간 240초를 사용했습니다. BTH의 최대 호출은 3회였지만 실제로는
양쪽 모두 한 번만 호출했습니다. 사람이 후보 코드를 고쳐 주지 않았습니다.

| 관찰 항목 | BTH | 직접 Codex |
| --- | --- | --- |
| 일반 테스트 | 63/63 통과 | 63/63 통과 |
| 별도의 기능 검증 | 9/9 통과 | 9/9 통과 |
| 작업 중 자체 검증 근거 | BTH가 소스에 묶인 검증 기록 생성 | 실행 관찰 없음 — 미확인 |
| 전체 작업 완료 판정 | 확인됨 | 미확인 (`null`) |
| 기록된 전체 시간 | 245.462초 | 195.773초 |
| provider 보고 총 토큰 | 433,044 | 449,071 |
| 그중 캐시 입력 토큰 | 375,040 | 396,800 |
| 달러 비용 | 미제공 | 미제공 |

위 시간과 토큰은 실행 당시 관찰값입니다. 직접 경로의 전체 흐름 완료가 미확인이고,
동일 과제 한 번의 순차 실행이라 캐시·실행 순서의 영향도 있습니다. **BTH가 빠르다거나
토큰 효율이 낫다는 결론으로 사용하지 않습니다.** 토큰 총량은 신규 청구 토큰 수와
같지 않으며 비용 미제공은 무료라는 뜻이 아닙니다.

두 후보 모두 기존 비밀번호 해시 처리기를 재사용하고, 존재하지 않는 계정에도 해시
확인을 수행하며, 비밀번호 복구 응답에서 계정 유무를 구분하지 않도록 수정했습니다.
정상 로그인·비밀번호 변경·비활성 계정 차단은 독립 테스트로 함께 확인했습니다.
실제 변경 5개 파일씩을 읽어 테스트 삭제·skip·검증 설정 약화가 없음을 확인했습니다.
이것은 해당 동작의 검증이지 서비스 전체의 일정 시간 실행이나 보안 안전성 증명이 아닙니다.

## 실전에서 찾은 잘못된 완료 판정과 수정

처음 평가기는 뒤에서 테스트가 통과하면 직접 CLI도 전체 작업을 끝냈다고 셌습니다.
하지만 당시 직접 실행의 검증 명령 관찰 수는 0이었습니다. 정말 실행을 생략했는지,
관찰기가 놓쳤는지는 남은 자료만으로 구분할 수 없습니다.

이를 감추거나 원본 성공 값을 덮어쓰지 않았습니다.

- [실제 실행 원본](artifacts/v42/codex-native-pair.json): 당시 코드 지문과 두 후보 결과를 그대로 보존합니다. 직접 경로의 원본 `successAt1: true`는 지금의 완료 판정으로 인정하지 않습니다.
- [별도 재판정](artifacts/v42/native-validation-audit.json): 같은 관찰 자료에서 직접 경로를 `taskAcceptanceSuccess: true`, `successAt1: null`로 나눴습니다. 새 모델 실행 결과가 아닙니다.
- 현재 코드: 승인된 명령의 명시적인 성공 종료가 관찰되지 않으면 직접 경로의 native 완료는 미확인입니다. `./tools/verify`와 `tools/verify` 같은 표현 차이는 인식하되, 명령을 읽거나 출력하기만 한 것은 실행으로 세지 않습니다.
- 마지막 경계 검사: `true || ./tools/verify`, `./tools/verify || true`처럼 검증을 건너뛰거나 실패를 숨길 수 있는 복합 명령도 성공으로 세지 않도록 수정했습니다. 명령 전체를 해석할 수 없으면 미확인으로 남깁니다.

새 관찰기도 운영체제 보안 경계가 아니며, 앞서 성공한 명령이 나중에 편집된 최종
소스까지 검사했다는 증거는 아닙니다. 최종 독립 검증은 여전히 필요합니다.
특히 Codex의 모든 셸 동작을 이 관찰기로 차단하거나 감지하는 것은 아닙니다.
수정 후 프로토콜은 `native-workflow-v42-observed-validation`으로 구분합니다.
수정된 관찰기로 새 실제 모델 쌍을 실행한 것은 아닙니다.

## 회귀 검증과 남은 목표

완료된 최종 검사 수치와 소스 지문은 [QA 기록](artifacts/v42/qa.json)에 남깁니다.
실제 검증 실패 → BTH의 두 번째 수정 호출 → 통과 경로도 테스트했습니다.
이 경우 모델은 대역이며, 진짜 모델의 자동 복구 성공 사례로 세지 않습니다.

- 전체 회귀: 612개 중 **608 통과, 실패 0, 4 skip**.
- 커버리지: 줄 91.45%, 분기 83.20%, 함수 98.72%. 새 예산·관찰 모듈의 줄 커버리지는 각각 100%입니다. 커버리지가 결함 없음을 증명하지는 않습니다.
- 의도적 결함 46개 모두 테스트의 실제 assertion 실패로 탐지했습니다. 선별한 사례의 mutation smoke이며 전체 가능한 변이 검사가 아닙니다.
- 패키지를 임시 위치에 설치한 실행 검사와 전체 구문 검사가 통과했습니다.
- 건너뛴 4개: 실제 MySQL DB, 실제 Maven/Gradle 통합, 실제 Windows provider 실행, 실제 Windows 자식 프로세스 종료. 이를 통과로 세지 않았습니다.

남은 일은 수정 후 실제 native 재비교, Claude의 native 전체 흐름 확인, 서로 다른
백엔드 3개·20개 작업의 비교 완료입니다. 실제 Windows, MySQL E2E, 두 개발자
인수인계도 이번 검사로 확인한 것이 아닙니다. 사전에 준비한 기획 결정·테스트 환경을
사용했으므로 낯선 회사의 기획을 읽고 인터뷰하는 시간과 정책 이해 정확도도 별도
검증이 필요합니다. **전체 제품 완료 또는 2배 성능을 주장하지 않습니다.**

## 재현과 원본 구분

실제 호출 명령은 아래와 같았습니다. 지금 실행하면 수정된 프로토콜로 새 결과가
나오므로 반드시 새 출력 디렉터리를 사용해야 합니다. 원본 기록 도구 `record.mjs`는
실행 당시 봉인된 소스만 허용합니다. 현재 코드로 옛 실행을 재생성하는 도구가 아닙니다.

```bash
BTH_PROVIDER_BENCHMARK=I_UNDERSTAND_PROVIDER_COSTS \
node scripts/benchmark-provider-comparison.mjs --execute \
  --workflow native-workflow --provider codex --lane both \
  --task fastapi-04-constant-time-login --mode deep --model gpt-5.6-sol \
  --timeout-ms 240000 --max-attempts 3 \
  --output /tmp/bth-native-new-run --allow-network --keep-workspace
```

회사 코드·운영 시스템·사용자 설정은 변경하지 않았고, 두 후보도 실제 프로젝트에
적용하지 않았습니다. 공개 증거에는 모델 출력·소스 본문 대신 지문·집계·공개 파일
경로를 남겼습니다. 후보 작업공간과 원본 관찰 자료는 감사용으로 보존했습니다.
