# v44 — Spring 실제 작업 흐름과 검증 준비 비용

## 이번 단계의 범위

Spring Petclinic의 이름 검색 공백 처리 과제를 고정한 뒤, 프로젝트의 전체
`./mvnw -o -B verify`를 유지한 채 BTH와 직접 Codex를 비교한다. 이것은
미리 검증 환경을 준비한 공개 프로젝트 실험이다. 낯선 회사의 기획·정책을
자동으로 정확히 이해했다는 증거나 전체 20개 과제 완료 판정이 아니다.

- 대상: `spring-02-owner-search-whitespace`
- 원본: `0f6e8614047bd74cf6223b4d8a858d2ed2824f8a`
- 정답: `bb37aad8c332264723817d855e8b3b96b7c392bc`
- 모델 실행은 동일한 명시적 fast/low 설정, 동일 모델, provider 시간 240초.
- BTH는 최대 3번 호출에서 복구하며, 직접 CLI는 한 세션 안에서 구현·검증한다.
  따라서 한 번의 모델 호출 성공률과 전체 요청 성공률을 섞지 않는다.
- 직접 CLI 내부 테스트는 provider 시간에 포함되고 BTH 외부 검증은 별도이므로
  동일한 사고 시간 예산 실험이라고 주장하지 않는다. 전체 완료 시간도 함께 본다.

## 실제로 확인한 준비와 실패

1. 첫 준비는 추가한 DB 환경 helper의 JavaFormat 위반으로 실패했다. 검사를
   끄지 않고 helper의 형식을 고쳤다. 원본 POM·production 코드·검사 명령은
   바꾸지 않았다. 이 단계에는 모델 호출이 없었다.
2. 원본 PostgreSQL 테스트의 고정 Compose 포트와 MySQL 공개 바인딩을 발견했다.
   해시와 원본 preimage가 고정된 테스트 전용 환경으로 바꿨다. 원래의 MySQL 2개,
   PostgreSQL 2개 테스트 메서드는 본문까지 동일함을 해시로 확인했다.
3. 실제 Maven 전체 검증: **71개 통과, 실패·오류·건너뜀 0개**. 코드 형식과
   checkstyle 검사, MySQL·PostgreSQL 통합 검사를 포함한다.
4. 독립 수용 검사: 원본에서 공백 처리 관련 2개 실패·나머지 4개 통과,
   정답에서 6개 모두 통과. 컴파일 오류를 기능 실패로 세지 않았다.
5. 전체 Git 이력을 중복 복사하던 수용 검사에서 ENOSPC가 발생했다. 함께 돌던
   첫 coverage 실행도 환경 오류로 무효화했다. 해당 로그를 통과 증거로 쓰지 않는다.

기계 판독 증거: [spring-baseline.json](artifacts/v44/spring-baseline.json).

## Git 복사 비용 개선

수용 검사의 base/target/candidate 복사본만 깊이 1인 로컬 fetch로 바꿨다.
요청한 원본 커밋 SHA와 그 파일 트리는 그대로 유지한다. 공유 object 경로,
hardlink, 원격 저장소 설정이나 불필요한 과거 이력은 새 검사 복사본에 없다.
후보의 미커밋 변경·추가·삭제는 기존 source-bound 복사 및 동등성 검사를 유지한다.

| 실제 Spring Git 객체 저장량 | 개선 전 복사 대상 | 개선 후 복사 대상 |
| --- | ---: | ---: |
| pack + index (`git count-objects`, KiB) | 783,327 | 476 |
| 객체 수 | 102,962 | 182 |

이는 약 99.94%의 **Git 객체 복사량 감소**다. 전체 프로젝트 디스크 사용량,
AI 토큰 절감 또는 전체 개발 속도 1,600배 향상을 뜻하지 않는다. 의존성 캐시와
빌드 산출물 공간은 별도로 필요하다. 원본 snapshot·symlink/submodule 차단·
미커밋 파일 보호·다른 이력 배제는 실제 Git을 사용하는 테스트로 확인한다.

## DB 환경의 보장 범위

- 이미 설치된 `mysql:9.7`과 `postgres:18.4`의 정확한 image ID를 조회해 사용한다.
  새 image pull이나 production 연결은 실험 경로에 넣지 않았다.
- 실행별 UUID 소유권 label, 임의 비밀번호, tmpfs 데이터, `127.0.0.1` 임의 포트.
- Docker가 없으면 준비 실패다. DB 검사를 건너뛰고 성공시키지 않는다.
- 정리 전 소유권·전체 container ID·image ID를 확인한다. 다른 소유자의 자원은
  지우지 않는다. 정상 종료에서는 Testcontainers가 정리했음을 추가로 확인한다.
- OS 수준의 egress sandbox, 강제 종료의 모든 경우, 실제 Windows CLI 실행을
  검증했다고 주장하지 않는다. Windows wrapper 선택은 계약 테스트 범위다.

## 모델 비교와 최종 회귀

실행 전에 23개 소스/설정/fixture hash를 봉인했다. 원본 결과는
[codex-native-spring-pair.json](artifacts/v44/codex-native-spring-pair.json)에 보존했다.

| 관찰 | BTH | 직접 Codex |
| --- | ---: | ---: |
| provider 호출 | 1회 | 1회 |
| 전체 요청 완료 | 확인됨 | CLI 종료로 실패 |
| 측정 시간 | 126.737초 | 중단까지 95.597초 |
| 보고된 총 토큰 | 164,891 | 미확인 |
| 달러 비용 | 미확인 | 미확인 |
| 원래 요청의 최종 검증 | 71개 통과 + 독립 6개 | 미완료 |

BTH의 71개는 기존 검색 테스트 하나를 공백 입력 회귀 사례로 바꾼 결과로,
새 테스트 메서드 수가 늘었다는 뜻은 아니다. 정상 입력·빈 값·내부 공백 보존은
별도의 독립 검사로도 확인했다. 수정은 controller와 그 테스트 두 파일뿐이고
원본 DB fixture·POM·검사 설정은 바뀌지 않았다. 마지막 검증과 최종 코드의
source fingerprint 일치도 확인했다. BTH의 총 토큰에는 캐시 입력 136,704가
포함되며, 비캐시 입력 26,595·출력 1,592다.

직접 Codex는 `.strip()` 처리와 별도 회귀 테스트를 작성했다. 승인된 검증 명령
시작 2회 중 실패 결과 1회만 관찰됐고 성공 종료는 관찰되지 않았다. provider는
시간 제한 240초 전에 exit 1로 끝났고, 마지막 사용량을 받지 못했다. 보존된
분류는 `provider-failed`뿐이므로 통신·서비스 제한·도구 실패 중 무엇인지는
특정하지 않는다. 이를 코드 품질 실패나 하네스의 속도·토큰 우위로 해석하면 안 된다.

직접 후보를 별도 임시 복사본에 복사해 코드를 고치지 않고 재검사했더니
**72개 전체 테스트와 독립 6개가 통과**했다. 원본 후보 fingerprint는 그대로다.
[추가 진단](artifacts/v44/direct-diagnostic.json)은 원래 provider 실행 완료나
빠진 사용량을 대신하지 않으며, 원래 실패 점수는 수정하지 않았다.

최종 회귀는 디스크 압력을 줄이기 위해 Node test concurrency를 4로 제한해 실행했다.
**620개 중 616개 통과, 실패 0개, 환경 의존 건너뜀 4개**. coverage는
line/statements 91.46%, branch 83.22%, function 98.73%다. 선별한 mutation
50개는 모두 assertion으로 검출했고 설치 smoke도 통과했다. exhaustive mutation,
실제 Windows provider/종료, 별도 MySQL reference와 JVM opt-in suite를 이번
기본 회귀 실행에서 검증했다고 주장하지 않는다. 실제 Spring JVM/DB 실행은 위
별도 증거로 구분한다. 최초 ENOSPC 회귀 로그는 무효 기록으로 남긴다.

## 전체 과제 현황

[현재 장부](artifacts/v44/corpus-ledger.json): 독립 정답 검사가 정의된 과제 11개,
서로 다른 이력상 모델 비교 9개 과제, native CLI 쌍대 시도 3개 과제,
양쪽 native 완료 확인 1개 과제다. CLI 시도 수에는 이번 중단처럼 사용량이
미확인인 경우도 포함하며, 측정 완료 모델 비교로 세지 않는다.

snapshot 구현이 바뀌었으므로 새 검사기 소스와 일치하는 정답 대조 검증은 현재
Spring 1개만 다시 확인했다. 과거의 10개 확인 기록을 지우거나 새로운 구현에서
전부 재검증된 것처럼 옮기지 않았다. 나머지 정답 검사 재실행도 남아 있다.
