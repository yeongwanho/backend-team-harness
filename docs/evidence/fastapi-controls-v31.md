# 세 번째 백엔드까지, 제대로 고쳤는지 판별하는 검사

목표는 **요구사항을 주면 프로젝트 규칙에 맞게 구현하고, 검증까지 끝내는 것**이다.
AI가 “완료했다”고 말하는 것만으로 점수를 매길 수 없으므로, 먼저 원래 코드에서
실패하고 정답 코드에서 통과하는 별도의 검사를 만들었다.

현재 Spring·NestJS·FastAPI의 **20개 과제 중 10개**가 이 대조 검증을 통과했다.
이는 검사 준비 범위이지 제품 완성도 50%나 AI 구현 성공 10건이라는 뜻이 아니다.
이번 체크포인트의 모델 호출은 **0회**다.

단언은 58개이며, 정답 코드에서 모두 통과했다. 각 실행 전후 소스가 같은지,
현재 검사 파일·판정기 해시와 일치하는지도 확인했다.
[현재 유효한 과제와 근거](artifacts/v31/control-index.json).

FastAPI는 실제 애플리케이션의 HTTP·JWT·비밀번호 해시·SQLModel·PostgreSQL을
통과시켰다. 메일 전송만 대역으로 바꿨다. 회원 복구 요청은 계정 존재 여부와
무관하게 같은 응답을 주되, 실제 있는 계정에만 메일 전송을 요청하는지 검사한다.
알 수 없는 계정의 로그인도 실제 해시 검증 함수를 호출하는지 확인한다.
**전체 응답 시간이 항상 같다는 증명은 아니다.** DB 경합·부하·배포 검증도 아니다.

## 판정기의 허점을 고쳤다

이전에는 JUnit의 `error`도 원래 기능이 잘못됐다는 증거로 인정할 수 있었다.
하지만 의존성 준비나 테스트 설정 실패도 같은 형식으로 기록될 수 있다.

이제 선택된 테스트의 명시적인 단언 실패가 있어야 하며, 보고서 어디에든
`error`가 있으면 대조 검증을 확정하지 않는다. 모든 오류의 원인을 자동으로
이해한다는 뜻이 아니라, **불분명한 오류를 점수에 넣지 않는 보수적인 기준**이다.
새 회귀 테스트가 수정 전 실패하는 것을 확인했고, 이 조건을 제거하는 mutation도
탐지했다. 정답과 후보의 통과 기준은 완화하지 않았다.

이 기준으로 기존 8개를 다시 돌리자 2개가 제외됐다. 검색 테스트는 잘못된
검색값을 받은 Mockito 대역이 `null`을 반환했고, 방문 등록 테스트는 ID 변조로
발생한 예외를 그대로 보고했다. 전자는 대역이 항상 유효한 페이지를 반환하게
하고 HTTP 응답·조회 인자를 검사했다. 후자는 **준비 단계가 끝난 뒤 실제 HTTP
요청이 예외 없이 처리돼야 한다는 단언**을 추가했다. ID·입력·응답 검사는 유지했다.

## 준비 실패도 숨기지 않는다

1. FastAPI 첫 실행: 오프라인 의존성 캐시가 부족해서 중단했다. 기능 실패로 세지 않았다.
2. 공개 lockfile의 호스트를 확인하고 빌드·프로젝트 설치 없이 필요한 wheel을 준비했다.
   두 공개 원본의 소스는 바뀌지 않았다. 실제 검사는 다시 오프라인으로 실행했다.
3. 두 번째 실행: Docker 20.10.17의 internal network에서 필요한 호스트 포트가
   게시되지 않았다. 생성한 자원은 정리하고, 아래 제한을 명시한 전용 bridge로 바꿨다.
4. 최초 7개 인증 검사 통과 뒤 비활성 사용자 검사 2개를 추가해 9개 전체를 재실행했다.
5. 새 Spring 검사는 처음에 프로젝트 포맷 검사에서 중단됐다. 포맷 검사를 끄지 않고
   캐시된 Spring JavaFormat 0.0.47로 두 검사 파일만 정리한 뒤 대조 검증을 통과했다.

## 임시 DB와 안전 경계

회사 저장소·회사 DB·개인 dotenv·실제 메일은 사용하지 않았다. 이 공개 FastAPI
프로젝트가 PostgreSQL을 사용하므로 해당 사례의 검사에서만 PostgreSQL 16을 썼다.
**하네스의 MySQL 우선 방향을 바꾼 것이 아니다.**

캐시된 이미지의 digest를 고정하고 pull을 금지했다. 임시 DB에 임의 비밀번호와
합성 데이터만 넣었다. 호스트 파일 마운트·영속 볼륨 없이 읽기 전용 컨테이너,
제한된 tmpfs·메모리·CPU·프로세스 수를 사용했다. 실행별 라벨로 소유권을 확인한
컨테이너·네트워크만 제거했고, 최종 라벨 조회 결과 남은 자원은 0개였다.
오프라인 테스트용 임시 Python 환경도 제거했다. 의존성 캐시는 남는다.

네트워크는 전용 bridge와 `127.0.0.1` 포트 게시 요청이다. **OS 수준 외부 통신
차단이 아니다.** Python socket 방어도 네이티브 DB 드라이버의 모든 통신을
통제하지 않는다. 특히 Docker 28 이전의 localhost 게시 제한을 완전한 호스트
격리로 보증하지 않는다. [Docker 공식 포트 게시 문서](https://docs.docker.com/engine/network/port-publishing/).
회사 코드나 비밀값을 이 공개 검사 환경에 넣어도 안전하다는 주장으로 확대하지 않는다.
