# 실패 이유를 전달하고, 테스트 설정 문제를 따로 고쳤다

목표는 기능을 많이 붙이는 것이 아니라, 작은 요구사항도 프로젝트 규칙을 지키며
구현·검증·안전 적용까지 끝내는 것이다. 이번에는 지난 이메일 충돌 수정의 실패를
그대로 이어받아 확인했다. **코드와 검사 설정을 보완한 재현 검증은 통과했지만,
실제 AI 자동 복구는 제한된 두 번의 호출 안에서 끝나지 못했다.**

## 어디서 막혔나

| 단계 | 관찰한 결과 | 이번에 확인한 것 |
|---|---|---|
| 이전 실패 코드를 다시 검사 | TypeScript TS2353, 실행된 테스트 0개 | 코드·파일·47행 7열이 실제 검사 → 기록 → 복구 요청까지 전달됨 |
| 실제 Codex 복구 1회 | 컴파일 오류 수정, 테스트 0개 | 기존 `src/...` import를 Jest가 찾지 못하는 별도 문제 발생 |
| 실제 Codex 복구 2회 | 여전히 테스트 0개 | 재시도 예산 소진, 실패 유지 |
| import 경로만 진단용으로 지정 | 후보 테스트 3개 통과 | 코드 수정 없이 검사 설정의 원인을 좁힘. 정식 통과로 세지 않음 |
| 새 설정 생성 후 같은 코드를 재현 | 후보 테스트 3개, 독립 검사 7개 통과 | 설정 생성 보완을 실제 코드로 검증 |
| 새 임시 프로젝트에 안전 적용 후 재검사 | 테스트 3개 통과, `VERIFIED` | 봉인된 후보의 적용 영수증과 적용 후 검증 확인 |

세 번째 단계까지의 실패는 지우지 않았다. 이후 단계는 **추가 모델 호출 0회**로
이미 만들어진 코드를 재사용했다. 따라서 최초 시도 성공률, AI의 독립적인 문제
해결 능력, 이전보다 빨라졌다는 성과로 합산하지 않는다.

## 바꾼 동작

### 1. 컴파일 오류의 위치를 다음 시도에 알려준다

기존에는 원문 로그를 제외하면서 유용한 오류 위치까지 없어졌다. 모델은
`junit_reports_missing`과 “테스트 0개”만 보고 고쳐야 했다.

이제 실패한 검사에서 TypeScript의 `TS2353` 같은 코드와 실제 존재하는 프로젝트
파일의 줄·열만 뽑는다. Java·Kotlin의 정해진 컴파일 출력 형태도 단위 테스트했다.
이번에 실제 컴파일러로 검증한 언어는 TypeScript뿐이다.

로그 본문·소스 발췌·임의 메시지는 보내지 않는다. 두 출력 스트림에서 각각
최대 64 KiB, 후보 64개, 최종 위치 16개로 제한한다. 없는 파일, 외부 경로,
심볼릭 링크, 탐지된 비밀값 형태는 버린다. 기록과 복구 요청을 만들 때마다 다시
검사한다. 이 정보는 **고칠 곳을 찾는 참고 정보**이지 성공 판정이나 실행 명령이 아니다.
검사 결과, 최소 테스트 수, 승인 범위, 재시도 횟수는 바꾸지 않았다.

### 2. 새 검사 설정이 명시된 import 기준 경로를 반영한다

실제 공개 저장소는 TypeScript에 `baseUrl: ./`를 선언했지만, 기본 Jest에는 같은
검색 위치가 없었다. TypeScript가 코드를 이해해도 Jest가 실행 중 모듈을 못 찾을
수 있었다. Jest의 `modulePaths`는 추가 검색 위치다. TypeScript의 모든 모듈 해석
규칙과 같다는 뜻은 아니다. [Jest 29.7 설정](https://jestjs.io/docs/29.7/configuration#modulepaths-arraystring),
[TypeScript baseUrl](https://www.typescriptlang.org/tsconfig/baseUrl.html).

`bth init`으로 **새로 생성하는 검사 설정**에만 다음 조건을 적용한다.

- 기본 `jest` 명령, package.json 안의 단순한 `ts-jest` 설정이어야 한다.
- `tsconfig.json`이 명시한 `baseUrl`이 실제 프로젝트 내부 디렉터리여야 한다.
- 외부 Jest 설정, 사용자 지정 resolver·mapper·modulePaths, preset·projects,
  TypeScript extends·paths, 애매하거나 안전하지 않은 입력은 자동 추론하지 않는다.
- tsconfig를 검증 입력에 포함한다. 구현 요청에도 추가된 검색 위치를 설명한다.
- 테스트 목록 확인과 최종 검사에 같은 검색 위치를 사용한다. 절대 경로는 실행
  시점에 계산하므로 공백이 있는 패키지 경로도 하나의 인자로 전달한다.

기존 설치된 검사 설정을 몰래 덮어쓰지 않는다. 이미 설정이 있는 프로젝트는
변경을 검토하고 명시적으로 갱신해야 한다. 지원 조건에 맞지 않으면 “문제를
해결했다”고 추정하지 않는다. 이번 보완은 모든 TypeScript 설정을 지원하는 기능이 아니다.

## 실제 AI 호출 비용도 남긴다

실패 후보 재생은 모델 호출이 아니다. 그 다음 두 번만 실제 `gpt-5.6-sol`, 빠른
모드의 Codex 호출이었다. 캐시 입력을 포함한 총 토큰을 숨기지 않았다.

| 실제 복구 호출 | provider 시간 | 총 토큰 | 캐시 제외 입력 | 최종 검사 |
|---|---:|---:|---:|---|
| 1 | 43.908초 | 162,698 | 26,595 | 실패 |
| 2 | 52.539초 | 207,246 | 30,959 | 실패 |

달러 비용은 provider가 제공하지 않아 `null`이다. 시간은 provider 호출 시간이며
환경 준비·별도 독립 검사·전체 작업 시간을 뜻하지 않는다. 복구 도중 드러난 모듈
해석 오류 자체는 아직 구조화된 복구 힌트로 전달하지 못한다. 이번에는 설정 생성기를
고쳐 해당 단순 구성의 원인을 제거했으며, 범용 런타임 오류 진단은 남아 있다.
[실제 실패와 사용량](artifacts/v30/paid-recovery.json).

## 검증 결과

- 전체 회귀: **477개 중 473 통과, 0 실패, 4 건너뜀**.
- 코드 커버리지: 줄 **90.68%**, 분기 **81.35%**, 함수 **98.85%**.
- 선택한 mutation **22개 모두 탐지**. 전체 코드의 mutation 점수는 아니다.
- 패키지 설치 스모크와 문법 검사 통과. 실제 설치 버전은 `0.9.0`이다.
- 실제 실패 코드에서 컴파일 진단 전달 확인. 새 후보의 생성 검사 3개 통과.
- 독립 검사: 수정 전 3개 실패·4개 통과, 정답 7개 통과, 재현 후보 7개 통과.
- 새 임시 프로젝트에 두 파일 안전 적용 후 3개 테스트 재실행, `VERIFIED` 확인.

첫 mutation 실행은 진단 누락 시 테스트가 assertion 대신 TypeError로 끝나
판정 불가였다. 누락 자체를 명시적으로 검사하도록 테스트를 고친 뒤, 22개 전체를
다시 실행했다. 통과 수를 만들기 위해 mutation 판정 조건을 완화하지 않았다.

커밋·별도 임시 프로젝트만 사용했고 회사 저장소는 수정하지 않았다. 원문 로그,
개인 로컬 경로, 소스 본문, 인증 정보는 공유 증거에서 제외했다.

## 아직 목표 완료가 아닌 이유

독립 과제 대조 검증은 여전히 **8/20개**, 실제 Codex를 시도한 서로 다른 과제는
**4개**다. 이번 재현 성공은 새 과제나 최초 시도 성공 표본을 추가하지 않는다.
3개 독립 백엔드·20개 작업에서 직접 Codex/Claude 대비 성공률·규칙 위반·영향
분석·시간·토큰·비용·재시도를 비교하는 전체 완료 조건은 남아 있다.

이번 실행의 네 가지 skip은 실제 MySQL, 실제 Maven/Gradle JVM, 실제 Windows
provider 실행, 실제 Windows 자식 프로세스 종료다. macOS의 경로 계약 테스트나
모의 컴파일 출력으로 이 항목을 통과했다고 주장하지 않는다. 독립 이메일 검사는
실제 서비스 클래스와 저장소 대역을 사용하며 DB 경합·운영 E2E 증명은 아니다.
Claude·Grok의 외부 재검토도 이번 체크포인트에서는 실행하지 않았다.
