# 코드 추천은 고쳤지만, 작은 작업의 속도 문제는 남아 있다

작은 API 수정도 회사 규칙과 주변 코드를 알아야 한다. 다만 그 준비 때문에
직접 AI에 시키는 것보다 오래 걸리면 곤란하다. 이번에는 이전 FastAPI 실측의
잘못된 추천을 고치고, 중복 입력을 줄인 뒤 같은 작업을 다시 실행했다.

**결론: 두 과제 모두 정답이지만 FastAPI에서는 BTH가 느렸고, Spring에서는 비슷했다.** 이번 수정을
“성능 최적화 완료”나 “직접 Codex보다 우수함”의 증거로 쓰지 않는다.

## 무엇을 고쳤나

이전 요청은 `test_users.py`를 `users.py`와 연결하지 못하고 빈 `__init__.py`
파일끼리 추천했다. 이름이 같은 파일이 여러 개면 마지막으로 읽은 파일을
골랐고, 테스트의 트랜잭션·경로·DB 설정도 실제 서비스의 규칙처럼 집계했다.

이제 Python의 `test_` 접두사와 JVM·JS 테스트 이름을 인식한다. 경로로 추정한
모듈과 언어군이 같은 후보 안에서 패키지·대응 폴더를 확인한다. 후보가 동률이면
선택하지 않는다. 빈 초기화 파일 이름만으로는 연결하지 않고, 테스트 파일은
실제 서비스의 계층·트랜잭션·경로·DB 집계에서 제외한다.
이는 새로 분석하는 관측에 적용하며, 과거 승인된 인터뷰 기록을 소급해서
덮어쓰지는 않는다.

이름 충돌이 아주 많을 때도 무한히 비교하지 않는다. 테스트 하나에 서로 다른
후보가 128개를 넘으면 “판단하지 못함”으로 남기며 그 수를 모델에도 전달한다.
합성 파일 1만 개(테스트 5천 개)의 충돌 검사 5회는 약 50~65ms였다. 이는 메모리
안의 분석 함수만 측정한 수치다. 저장소 읽기나 AI 실행 속도가 아니다.

승인 계획은 **한 글자도 줄이지 않았다.** 현재 생성기가 만든 컨텍스트와
계획이 정확히 일치하고, 확정된 계획의 해시까지 맞을 때에만 중복된 요구사항·
허용 범위·DB 영향·제약 설명을 컨텍스트에서 제거한다. 주의할 사실과 규칙은
남긴다. 사람이 문장을 추가했거나 구형 형식·해시 불일치면 전체 원문을 보낸다.

이전 실제 요청을 같은 소스에서 재구성하면 18,209→17,435바이트(줄바꿈 제외),
약 **4.3% 감소**했다. 실제 새 실행 요청은 줄바꿈 포함 17,436바이트였다.
원래 승인 계획·규칙·검증 계약·권한 경계가 그대로인지 별도로 대조했다.
[재현 결과와 소스 해시](artifacts/v34/context-replay.json).

## 실제 Codex 비교

과제는 이전과 같다. “관리자가 없는 사용자를 읽으면 404를 반환하고,
기존 조회와 일반 사용자의 403 권한 거부를 유지하며 회귀 테스트를 추가한다.”
같은 공개 원본 커밋, Codex 0.151.0, `gpt-5.6-sol`, 빠른 모드, 최대 1회 시도다.
이번에는 직접 Codex → BTH 순서로 실행했다. 각 비교군은 별도 임시 clone과
동일하게 준비된 Python 환경·임시 PostgreSQL·검증 파일을 사용했다.

BTH가 약 26초 더 걸렸다. 이전 BTH 기록보다 총 토큰은 적지만, 캐시를 뺀
입력은 줄지 않았고 실행 시간은 늘었다. 각 1회뿐인 순차 관찰이므로 입력 축소가
특정 시간·토큰 변화를 일으켰다고 단정할 수 없다. 캐시·응답 변동도 통제하지 못했다.

두 후보 모두 라우트와 회귀 테스트 두 파일만 변경했다. 원래 55개 테스트가
남아 있고, 평가 환경의 메일 테스트 2개와 새 회귀 테스트까지 실행됐다. 모든
보호된 검증 입력을 당시의 봉인된 준비 기록과 바이트 단위로 대조해 동일함을
확인했다. 이번 직접 실행에는 v33 후반에 추가했던 전이적 입력 보호도 적용됐다.
[검증 입력·테스트 보존 근거](artifacts/v34/codex-integrity.json).

표의 위반 0은 관찰 범위 안의 결과다. provider 활동 추적기는 BTH 실행에서
읽기 명령을 0개로 집계했다. 이것을 “아무 코드도 안 읽었다”는 뜻으로 해석할 수는
없다. 모든 도구 형식을 완전하게 관찰한다고 검증하지 못했다. 영향 분석의
Recall/nDCG도 BTH가 제안한 경로와 직접 실행의 관찰된 읽기 경로를 쓰는 서로 다른
대용 지표다. 둘 다 1.0이어도 모델의 이해력이나 완전한 규칙 준수를 증명하지 않는다.

## 새로운 Spring 과제로도 비교했다

공개 Spring Petclinic의 이름 검색에서 앞뒤 공백만 제거하는 과제다. 빈 값·
누락된 값의 전체 검색, 이름 내부 공백·대소문자, 검색 결과가 없을 때의 동작은
유지해야 한다. 같은 Codex 모델·빠른 모드·1회 시도로 BTH → 직접 실행 순서로
비교했다. 공통 준비 후 71개 기본 테스트가 통과했고, 독립 검사는 원래 코드에서
목표 회귀 2개가 실패하고 정답 코드에서 6개 모두 통과하는 것을 먼저 확인했다.
[새 임시 clone의 사전 대조](artifacts/v34/spring-preflight.json).

둘 다 컨트롤러와 기존 테스트 클래스만 변경했다. 실제 diff를 읽어 null 처리와
기존 흐름을 유지하면서 문자열을 정리하는 같은 구현임을 확인했다. 기존 71개
테스트가 모두 남아 있고 새 테스트가 1개씩 추가됐다. upstream의 Testcontainers
MySQL 통합 테스트 2개와 PostgreSQL 통합 테스트 2개도 제외 없이 통과했다.
이는 그 프로젝트의 조회 테스트이며, BTH MySQL Pack 전체나 migration·락·성능을
검증했다는 뜻은 아니다. [실행·토큰·테스트 보존 근거](artifacts/v34/spring-pair.json).

약 2초 차이는 안정적인 속도 우위라고 볼 수 없다. BTH의 캐시 제외 입력은
오히려 조금 더 많았다. 영향 경로의 nDCG@20도 BTH 0.57, 직접 실행 1.0으로
집계됐다. 앞서 설명한 서로 다른 경로 지표의 한계까지 포함해 그대로 남긴다.
준비·사전 검증 일부는 로컬 변이 검사와 겹쳤으므로 전체 시간은 전용 성능
측정 환경의 수치가 아니다.

## 완료 범위와 다음 확인

전체 회귀 테스트는 530개 중 526개 통과, 실패 0개, 환경 조건상 제외 4개였다.
코드 줄 커버리지는 90.99%, 분기는 82.26%, 함수는 98.90%다. 선정한 변이 검사
33개를 모두 잡았으며, 패키지 설치·구문·CLI 문서 계약 검사도 통과했다.
변이 33개는 전체 코드의 변이 점수가 아니다. 실행 의존성 취약점 검사는
보고된 항목 0개였으며, 이것도 취약점 부재를 보증하지 않는다.
[QA 명령·소스 해시·실패 재현·제외 항목](artifacts/v34/qa.json).

이번 수정은 전체 목표의 한 단계다. 20개 과제 전체 구현 비교, 실제 Windows
provider/프로세스 종료, 회사 프로젝트 적용, MySQL 실환경 일반화는 완료하지 않았다.
공개 FastAPI의 PostgreSQL 사용은 평가 대상의 요구사항이며 MySQL 우선 방향을
바꾸지 않는다. OS 수준 네트워크 격리나 운영 DB 안전성을 검증한 것도 아니다.

다음에는 아직 실행하지 않은 과제로 범위를 넓히고, 준비·모델·검증 시간을
분리해 병목을 찾는다. 활동 관찰기의 누락 형식도 확인해야 한다. 속도를 위해
필수 규칙이나 검증을 빼는 것은 해법으로 채택하지 않는다.
이번 검사 중 로컬 디스크 여유가 약 4.8GB로 확인됐다. 사용자 파일·공용 캐시를
삭제하지 않았으며, 더 큰 실험 전에 증거 보존과 임시 환경 정리 범위를 정해야 한다.
