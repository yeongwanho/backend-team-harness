# v45 — Nest 검증 준비와 불필요한 디스크 점유 개선

## 무엇이 나아졌나

검사 하나가 끝나면 그 검사를 위해 만든 임시 복사본을 바로 정리한다.
기존에는 변경 전·후·후보 검사가 모두 끝날 때까지 세 복사본을 붙잡았다.
이제 결과와 소스 해시를 기록한 단계는 다음 단계 전에 지운다. 원본의 수정 파일,
미추적 파일, 공유 캐시와 이전 구현 후보는 정리 대상이 아니다.

이 개선은 **독립 수용 검사 내부의 동시 점유**를 줄인다. 개발 프로젝트 전체,
provider 작업 공간, 의존성 자체가 가벼워졌거나 AI가 빨라졌다는 뜻은 아니다.
정상·예외 경로와 원본 보존을 실제 Git 회귀 테스트로 검증하고, 정리를 제거한
mutation도 테스트가 잡는지 확인한다.

## 문서 저장소의 실제 버그를 잡는 검사

`nest-04-document-find-update`는 DB 수정은 됐는데 호출자에게 **수정 전 값**을
돌려주는 문제다. 원본과 정답 커밋을 각각 복사해 같은 독립 검사를 실행했다.

| 실행 경로 | 확인하는 동작 |
| --- | --- |
| 사용자 저장소 | 변경된 이메일 반환, 원래 ID·다른 필드 보존 |
| 세션 저장소 | 변경된 hash 반환, 사용자 연결·생성 시각 보존 |
| document-resource 생성 템플릿 | 실제 렌더링한 저장소·mapper가 변경 후 시각 반환 |
| all-db-resource 생성 템플릿 | 위와 같은 계약을 별도 생성 경로에서도 확인 |

각 경로에서 정상 갱신, 처음부터 문서 없음, 갱신 중 문서 소실, 조회 실패,
갱신 실패를 확인한다. **변경 전은 4개 실패·16개 통과, 변경 후는 20개 통과**다.
처음부터 없을 때 사용자·세션은 null을 반환하지만 생성 코드는 오류를 던진다.
이 기존 차이를 임의로 통일하지 않았다. `{ new: true }`라는 정확한 문구만 찾는
검사가 아니라 실제 반환값을 검사하고 동등한 return 옵션도 허용한다.

범위는 명확하다. 실제 repository와 mapper를 실행하되 Mongoose 호출은 대역이다.
도메인 decorator용 DB 모드도 합성 설정이며 비밀번호를 읽지 않는다. 생성 코드는
원본 EJS와 mapper를 렌더링·컴파일하지만 전체 Hygen CLI를 구동한 것은 아니다.
실제 MongoDB, 앱 부팅, 전체 생성 프로젝트 컴파일을 통과했다고 주장하지 않는다.

처음 검사 작성 중에는 import 시 DB 환경 검증 때문에 0개 테스트로 실패했다.
이를 버그 재현으로 세지 않고 설정 경계를 명시한 후 실제 assertion 실패를 확인했다.
증거: [nest-document-controls.json](artifacts/v45/nest-document-controls.json).

## 테스트가 하나도 없는 프로젝트는 어떻게 처리하나

`nest-06-user-email-conflict` 원본에서 `init`이 만드는 검증을 그대로 고정했다.
package.json·lockfile·테스트 검색 범위·실제 소스·기존 테스트는 바꾸지 않았고,
통과하는 가짜 테스트도 추가하지 않았다. 실행 파일은 이미 검증 소스 지문에
포함되므로 `inputs`에 중복 기재해야만 fixture를 인정하던 불일치만 고쳤다.

실제 오프라인 설치와 Jest 실행 결과:

- 실행된 단위 테스트 **0개**, 따라서 기본 검증 **미통과**.
- 별도 `--listTests --json --no-cache` 실행으로 빈 목록을 확인.
- 검사 전후 소스 지문과 고정 검증 파일은 동일.
- “첫 테스트를 작성해 볼 수 있음”으로만 분류. 최종 완료에는 실제 실행된 테스트
  1개 이상과 독립 과제 검사의 통과가 필요하다.

최종 증거: [nest-empty-baseline-final.json](artifacts/v45/nest-empty-baseline-final.json).
처음의 단일 작업 폴더 진단과 중간 Git 진단도 별도 파일로 보존했다. 최종 진단은
생성된 프로젝트를 커밋하고 새로 복사한 후 실제 오프라인 설치와 Jest를 실행했다.
추가로 `autocrlf=true` 복사본에서도 고정 wrapper와 verification JSON이 같은지
검사했으며, 두 Git 경계 모두 통과했다.
이것은 구현 성공이 아니며 이번 단계의 구현 비교용 provider 호출은 **0회**다.

## 전체 Nest 비교를 실행하지 않은 이유

단일 진단에서 설치한 의존성은 약 **457MiB**였다. 첫 진단의 디스크 여유는
설치 전 약 912MiB, 설치 후 약 421MiB였고, 최종 재검증은 약 710MiB에서
218MiB로 줄었다. 부모·격리 구현·독립 검사에 필요한 의존성을
함께 유지할 공간이 부족해서 BTH/direct 전체 비교는 시작하지 않았다.
첫 document 과제의 빠진 공개 패키지는 lockfile에 고정된 버전을 스크립트 실행
없이 준비했고, 정식 독립 검사는 다시 오프라인 설치로 실행했다.

이번에 만든 진단 복사본만 정리했고 로그와 해시를 남겼다. 사용자 데이터,
기존 캐시, 이전 provider 후보를 삭제하지 않았다. 이 환경에서는 3GB 이상
여유를 확보한 뒤 전체 비교를 다시 시도하는 편이 안전하다.

## 남은 판정

20개 과제·세 백엔드의 전체 구현 비교 목표는 그대로 미완료다. 이번 단계는
새 독립 검사와 실제 빈 테스트 기준선, 임시 공간 관리의 진척이다. native 요청
성공률·속도·토큰·비용 우위나 회사 정책 이해도를 새로 입증한 것으로 세지 않는다.

현재 소스로 이전 독립 검사 11개도 재실행했다. 10개는 원본의 assertion 실패와
정답의 통과가 성립했다. `nest-01-session-update-by-hash`는 현재 npm에서
package/lock 불일치(`gcp-metadata` 누락)로 양쪽 모두 설치 단계에서 멈췄다.
테스트 0개를 버그 재현이나 정답 통과로 세지 않았고 원본 lockfile도 바꾸지 않았다.
새 문서 검사를 합치면 정의된 독립 검사 **12개 중 11개**의 타당성을 확인했다.
이는 BTH가 11개 과제를 구현했다는 뜻이 아니다.

최종 회귀는 **627개 중 623개 통과, 실패 0개, 환경 의존 건너뜀 4개**다.
line/statements 91.40%, branch 83.19%, function 98.60%이며 선별한 mutation
53개를 모두 assertion으로 검출했고 Git 변환 오류 재발까지 포함했다.
최초 mutation 실행은 일반 Error였으므로
검출 성공으로 세지 않고 명시적 assertion을 추가한 뒤 전체 mutation을 재실행했다.
Git staging 직전에는 Windows wrapper가 CRLF에서 LF로 바뀌어 고정 해시가
깨지는 문제도 발견했다. fixture와 생성된 `.backend-harness/` 내부 계약 파일에
`-text` 속성을 두고 실제 Git blob이 원래
바이트와 같은지 검사했다. 이미 정규화되어 stage된 blob도 다시 반영한 뒤 해시를
확인했다. 반대로 강제 text 변환은 해시가 달라지는 양성 대조군도
확인했다. JSON 설정과 LF인 실행 스크립트도 자동 변환으로 해시가 달라질 수
있으므로 함께 보존한다. 이 Git 속성 파일 자체도 검증 입력으로 보호하고, 다른
회사 소스 디렉터리의 Git 설정은 바꾸지 않는다. Git `autocrlf=input/true/false`
세 설정을 검증한 것이며 Windows OS
자체를 실행했다는 뜻은 아니다.

이 수정 후에는 관련 40개 테스트를 다시 통과했다. 설치 smoke와 문법·문서
계약 검사도 통과했다. 선별 mutation은 전체 mutation 검증이나 무결함 보증이 아니다.
