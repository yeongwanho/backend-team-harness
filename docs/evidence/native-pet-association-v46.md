# v46 — 실제 구현 비교와 JVM 검증 파일의 Git 변환 결함 수정

이번에는 Spring의 “기존 반려동물을 중복 없이 연결하고 이름을 30자로 제한하기”를
실제로 구현시켰다. **코드는 양쪽 모두 기능 검사를 통과했지만, 작업 전체 성공은
아직 확인하지 못했다.** BTH가 더 빠르거나 토큰을 덜 쓴다는 결과도 아니다.

## 같은 과제로 비교한 결과

과제는 고정된 20개 중 `spring-01-pet-association`이다. 원본은
`88e37c15cf6fc8490b01bc3e8e2c800cec1ac272`, 정답은
`676db04515ee5f289641cea6cb379dc02b40f67f`이며 요구사항을 바꾸지 않았다.
정답 이력·독립 검사는 모델에게 주지 않았다. 동일한 Codex 모델
`gpt-5.6-sol`, fast/low 설정, provider 시간 예산 240초를 사용했다.
BTH는 이 예산 안에서 최대 3회 호출할 수 있고 직접 Codex는 한 세션이다.

| 확인 항목 | BTH | 직접 Codex |
| --- | --- | --- |
| 실행한 모델 호출 | 2회, 재시도 1회 | 1회, 세션 내부 수정 횟수 미측정 |
| 최종 후보 전체 테스트 | 77개 통과 | 77개 통과 |
| 원래 비교의 독립 기능 검사 | 규칙 판정 때문에 실행 대상에서 제외 | 10개 통과 |
| 작업 전체 판정 | 실패 | 미확인 |
| 구현·검증 구간 시간 | 217.084초 | 209.449초 |
| 준비·독립 검사 포함 전체 시간 | 264.205초 | 257.943초 |
| 전체 토큰 | 미측정 | 381,412 |

BTH의 첫 호출은 약 60초 후 비정상 종료했고 사용량을 반환하지 않았다.
두 번째 호출의 277,455토큰만으로 합계를 만들지 않았다. 첫 호출 이벤트에서
검사 명령 실행 1건이 감지되어 원래 비교의 규칙 판정을 통과하지 못했다.
이 분류는 명령 이벤트에 대한 휴리스틱이며, 저장된 집계·해시만으로 명령 원문이나
중단 원인을 확정할 수는 없다. 이 한계를 감추거나 임의로 성공으로 바꾸지 않았다.

직접 Codex는 승인된 검사 명령을 두 번 시작했지만, 관찰된 종료는 두 번 모두
실패였다. 이후 평가자가 최종 소스를 검사한 결과는 통과했다. **평가자의 통과를
Codex 세션이 검증까지 끝냈다는 증거로 대체하지 않았다.**

두 후보의 production 변경은 같았다. 기존 `getPet(id)`를 재사용해 같은 객체와
같은 저장 ID의 중복을 막고, 기존 필수값 검사를 유지하면서 길이를 검사한다.
직접 후보는 HTTP 입력 회귀 테스트도 추가했다. 정답 커밋에 없는 파일을
수정했다는 이유만으로 그 테스트를 불필요한 변경으로 판단하지 않았다.

BTH 후보를 수정하지 않고 별도 복사본에서 독립 검사를 추가로 실행한 결과도
10개 통과였다. 이것은 **사후 코드 진단**이며 원래 실패 점수를 덮어쓰지 않는다.

토큰에는 캐시 입력이 포함된다. 직접 후보는 캐시 입력 324,096, 비캐시 입력
52,933, 출력 4,383토큰이다. 달러 비용은 양쪽 모두 미측정이다. 직접 CLI의
내부 검증은 provider 시간에 포함되지만 BTH 외부 검증은 별도이므로, 같은 사고
시간이나 전체 성능 우위를 입증한 실험으로 볼 수 없다.

## 검사 자체가 결함을 잡는지 확인했다

기존 테스트를 단순히 복사하는 대신 아래 경계를 독립 검사 10개로 확인한다.

- 저장된 객체 연결, 같은 객체·같은 ID의 중복 방지.
- 서로 다른 저장 ID와 아직 ID가 없는 서로 다른 객체는 각각 보존.
- 정확히 30자는 허용하고 31자는 거절.
- 이름·종류·생일의 기존 필수값 규칙과 저장된 객체의 기존 예외 유지.

실제 원본은 **7개 실패·3개 통과**, 정답은 **10개 통과**했다. 전체 Maven
기준선은 73개 통과였고, 이 수를 모델 실행 전 최소 실행 개수로 고정했다.
원래 MySQL·PostgreSQL 통합 테스트 본문과 전체 `verify` 절차도 유지했다.
DB 환경은 기존 캐시 이미지와 작업별 임시 인스턴스다. 운영 DB는 사용하지 않았다.

검사가 허술한지도 확인했다. 정답의 임시 복사본에서 동일 객체 검사 삭제,
동일 ID 검사 삭제, null ID끼리 병합, 길이 한도 29·31이라는 다섯 오류를 각각
넣었다. **5개 모두 의도한 assertion 실패로 검출했다.** 컴파일·설치 오류는
검출 성공으로 세지 않았다. 전체 mutation 분석이나 무결함 보증은 아니다.

## 실행 중 발견한 제품 결함은 따로 고쳤다

검증 파일은 해시로 보호한다. 그런데 Spring의 Git 규칙은 `.cmd` 파일의
줄바꿈을 바꾼다. 같은 내용을 Git으로 복사했을 뿐인데 바이트가 달라져 검증
계약이 깨질 수 있었다. 앞선 보호 설정은 Node·Python 초기화에만 있었고
Maven·Gradle에는 빠져 있었다.

이제 모든 초기화 경로에서 `.backend-harness/` 내부 파일에만 바이트 보존
설정을 적용한다. 생성된 검증 입력에도 이 설정을 포함한다. 회사 소스의
최상위 `.gitattributes`는 바꾸지 않으며, 팀이 이미 작성한 내부 설정도 기본적으로
덮어쓰지 않는다. 명시적 `--force`에서는 기존 파일을 백업한다.

실제 Spring 원본으로 Git 복사 대조군을 실행했다.

- 보호 설정이 있는 복사본: 검증 fixture 일치.
- 같은 임시 원본에서 보호 설정만 뺀 복사본: `.cmd`가 103바이트에서
  107바이트로 바뀌고 고정 해시 검사 실패.

Maven·Gradle·Jest·미감지 프로젝트 각각에서 Git `autocrlf=input/true/false`
조합을 검증했다. 설정 보존·백업·심볼릭 링크 거절도 확인했다. 수정 전 회귀
검사는 6개 중 5개 실패했고, 수정 후 관련 21개 검사는 모두 통과했다.
이는 macOS에서 실제 Git을 실행한 결과이며 실제 Windows 실행 결과는 아니다.

이 수정은 원래 모델 비교가 끝난 뒤 적용했다. 보존한 모델 후보를 수정하거나
원래 결과를 재채점하지 않았다. Git 결함이 첫 호출 중단이나 명령 이벤트 판정의
원인이었다고 단정하지도 않는다.

[실제 Spring Git 대조군과 회귀 근거](artifacts/v46/spring-git-contract.json)

수정 후 전체 회귀는 **634개 중 630개 통과, 실패 0개, 환경 의존 건너뜀 4개**다.
line/statements 91.42%, branch 83.23%, function 98.60%로 기준을 통과했다.
건너뛴 항목은 선택 실행형 DB/JVM E2E와 실제 Windows 실행 두 건이다.
위에서 별도 수행한 Spring 실험과 기본 회귀의 건너뜀을 섞어서 모두 통과했다고
말하지 않는다. 설치 smoke(0.9.0), 문법과 최종 문서 계약 검사도 통과했다.

## 아직 끝나지 않은 것

목표는 여전히 세 백엔드·20개 과제의 전체 작업 흐름 비교다. 지금까지 native
쌍대 시도는 4개 과제, 양쪽 완료가 확인된 것은 1개 과제다. 검사 기준이 준비된
12개 중 현재 타당성이 확인된 11개를 구현 완료 수로 세지 않는다.

다음에는 중단된 호출의 사용량·원인과 검사 명령 실패 근거를 더 잘 남겨야 한다.
원래 소스가 아닌 보존된 복사본에서 직접 CLI 검증 실패도 재현해야 한다.
DB 변경 과제, 부족한 독립 검사, Nest의 전체 구현 비교, 회사별 정책·인터뷰,
실제 Windows와 개발자 간 인수인계 검증도 남아 있다. 이 결과를 완성도
백분율이나 “OMO보다 두 배”라는 주장으로 바꾸지 않는다.
