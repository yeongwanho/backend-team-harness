# 실패 진단 개선과 실제 Nest 작업 완주

이번에는 실제 공개 NestJS 작업 한 건에서 **격리 구현 → 테스트 → 독립 검사 →
임시 프로젝트 적용 → 재검증 → DONE**까지 확인했다. 전체 하네스의 완성을
뜻하지는 않는다. 특히 적용 이력 버그는 실제 실행 중 발견해서 고쳤으며,
처음부터 모든 단계가 성공한 것처럼 기록하지 않았다.

## 무엇을 고쳤나

- 컨트롤러가 `domain/` 파일을 import하면 그 컨트롤러도 엔티티로 분류되던
  오탐을 고쳤다. 파일 경로와 코드 본문을 분리하고 주석·문자열 안의 가짜
  선언을 제외한다. 제한된 패턴 분석이며 AST/실행 의미 분석은 아니다.
- `bth work`가 구현 중 실패했을 때도 `bth diagnose`로 볼 수 있게 했다.
  의존성 준비 실패는 모델 시도 0회로, 테스트 실패는 검사 코드·개수·실패한
  테스트 이름·프로세스 종료 상태로 구분한다. 변조된 기록은 거부한다.
- 다음 구현 시도에도 같은 제한된 실패 정보를 전달한다. 원문 로그와 assertion
  본문을 보내지 않으며 이름은 비밀 제거와 길이 제한을 적용한다. 모든 개인정보를
  완벽히 제거한다는 보장은 하지 않는다.
- 모델에게 보내는 패키지 목록은 선택된 코드 주변을 우선하고 모드별로 제한했다.
  선언된 규칙, 승인 계획, 코드 목록 순서, 근거는 유지한다. 생략 개수와 전체
  관찰 기록 위치를 함께 남긴다.
- 실제 `implement apply`에서 빠졌던 작업 이력의 `apply` 허용 항목을 추가했다.
  기존 테스트는 파일 복사만 확인했다. 이제 해시로 연결된 적용 이벤트도 확인한다.
- 요청에 포함된 지식 문서 수가 잘못된 필드 때문에 0으로 집계되던 오류를 고쳤다.
  이번 실제 요청에는 7개가 있었다. 원래 관측값과 요청 기반 정정을 별도로 보존했고,
  이 카운터를 고치기 위해 모델을 다시 호출하지 않았다.

## 문맥 크기 측정

같은 공개 Nest revision과 fast 설정을 모델 없이 실행해 요청만 채집했다.
compact JSON UTF-8 기준 **21,068 → 18,632바이트, 약 11.6% 감소**다.
요구사항·승인 계획, 프로젝트 규칙, 권한 경계, 선택 코드 목록은 전후가 동일했다.
토큰 절감률이나 속도 향상률로 바꿔 부르지 않는다.

## 실제 구현 결과

대상은 `brocoders/nestjs-boilerplate`의 `nest-02-file-relational-mapper`다.
기준 revision은 `07ac5f29d3032bb173fd538c549966e7eb96dcff`이며,
모델에게 기준 수정본과 독립 검사용 파일을 제공하지 않았다.

- Codex CLI 0.151.0, `gpt-5.6-sol`, fast, 최대 시도 1회.
- production 파일 2개와 회귀 테스트 파일 2개를 수정/추가했다.
- 작성한 테스트 **2/2 통과**, 모델에게 숨긴 독립 검사 **7/7 통과**.
- 격리 구현의 success@1은 true, 재시도 0회, 측정된 규칙 위반 0건.
- provider 총 토큰 220,021: uncached input 33,754, cached input 183,552,
  output 2,715. 달러 비용은 제공되지 않아 미측정이다.
- 구현·자체 검증 구간 96,604ms, provider 보고 시간 80,176ms,
  사전 준비·독립 검사까지 포함한 비교 실행 전체는 234,393ms였다.
  전체 하네스 회귀 검사가 같은 시간대에 실행됐으므로 통제된 속도 비교가 아니다.
- 입력 코드 검색 Recall@5는 **0**, Recall@20은 **0.5**다. 모델이 추가로 코드를
  읽어 성공한 사례이지, 하네스의 영향 분석이 완전해졌다는 증거가 아니다.

이전 v26의 실패 기록은 그대로 유지한다. 이번 한 번의 성공으로 일반적인 성공률,
직접 Codex 대비 우위, 문맥 축소의 인과 효과를 주장하지 않는다.

## 마지막 적용 단계에서 찾은 실제 버그

최초 적용은 네 파일의 내용 검증에는 성공했지만 작업 이력 저장이 거부돼 CLI가
exit 2를 반환했다. 이때의 receipt와 실패를 별도로 남겼다.

회귀 테스트에서 `lifecycleRecorded: false`를 재현하고 저장기의 허용 항목을 고쳤다.
모델이 만든 후보는 격리 worktree에 보존했다. 임시 프로젝트의 네 경로만 정확한
base로 되돌린 후 다시 적용해 **exit 0, 적용 이력 저장 성공**을 확인했다.
이어 일반 `bth verify`가 실제 테스트 2개를 다시 실행해 VERIFIED가 됐고,
소스 재확인을 거쳐 임시 작업이 DONE으로 전환됐다. 회사/원본 upstream에는
쓰거나 push하지 않았다.

## 검증 범위와 남은 일

최종 회귀·커버리지·mutation·설치 결과와 소스 해시는
[QA 기록](artifacts/v27/qa-context.json), 실제 모델·독립 검사·적용 결과는
[Nest 실행 기록](artifacts/v27/retained-nest-run.json)에 있다.

- 실패 테스트에서 원인을 제거하면 다시 통과하는지 확인했다: 역할 분류,
  구현 진단 부재, 적용 이력 부재, 문서 수 집계 오류.
- 원문 로그 제외·비밀 제거·자료 크기 제한·기록 변조·원본 변경·준비 중 소스
  변경·재시도 예산·이전 verify 진단 경로를 회귀 검사한다.
- 실제 모델의 실패 후 자동 수정은 이번 건에서 발생하지 않았다. 테스트 fixture의
  두 번째 시도 성공을 실제 모델 복구 성능으로 계산하지 않는다.
- 실제 Windows, 실제 MySQL/기본 JVM opt-in 검증은 이번 실행 범위 밖이다.
  소스 패턴 관찰도 모든 런타임 연결/회사 규칙을 이해한다는 뜻은 아니다.
- 3개 독립 백엔드·20개 과제의 Codex/Claude 대조 평가와 도입 목표는 아직 미완료다.
  이번에는 Codex의 기존 과제 한 건을 재검증했으며 새로운 독립 과제 수를 늘리지 않았다.
