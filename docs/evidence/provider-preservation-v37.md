# v37 — 정당한 변경을 막는 회귀 수정과 실제 비교

## 결론

v36의 "기존 조건이 달라지면 테스트 전에 중단"은 너무 강했습니다.
요구사항이 그 조건을 바꾸라는 경우에도 구현을 되돌리게 만들었습니다.
v37은 **테스트 결과**와 **변경된 조건에 대한 사람의 판단**을 분리합니다.
테스트가 통과해도 검토가 남으면 작업 완료로 표시하거나 자동 적용하지 않습니다.

실제 비교에서는 v36 BTH가 직접 Codex보다 좋지 않았습니다. 이 실패를
성공으로 다시 계산하지 않았고, 이번 수정만으로 모델의 구현 능력이나
토큰 효율이 높아졌다고 주장하지 않습니다.

## 수정 전 실제 Codex 비교: 같은 반려동물 수정 작업

동일 공개 Spring 저장소/요구사항, `gpt-5.6-sol`, fast, 각 1회 실행입니다.
두 경로 모두 같은 기본 검증과 독립 행동 테스트를 사용합니다.
실행 런타임은 `a4f0b674` / `preservation-runtime-v36`이며,
측정 도중 런타임 코드를 변경하지 않았습니다.

이 비교는 **모델이 한 번 구현하고 공통 평가기가 검증하는 통제 실험**입니다.
양쪽 모델 모두 빌드·테스트·포맷 명령을 직접 실행하지 않도록 지시했습니다.
따라서 사용자가 평소 Codex에 테스트와 수정까지 모두 맡기는 자연스러운
전체 작업 흐름과는 다릅니다. 제품의 실제 시간 절감 주장을 하려면 그
전체 흐름의 별도 기준선도 필요합니다.

| 항목 | BTH | 직접 Codex |
|---|---:|---:|
| 첫 시도 성공 | 실패 | 성공 |
| 필수 테스트 | 구조 검사에서 중단, 미실행 | 58개 통과 |
| 독립 행동 테스트 | 최초 측정에서는 미실행 | 5개 통과 |
| 캐시 포함 총 토큰 | 373,073 | 272,736 |

BTH의 짧은 흐름 시간은 테스트를 못 했기 때문입니다. 속도 우위가 아닙니다.
두 경로의 흐름 시간은 구현과 필수 검증까지이며, 사전 환경 준비와 독립
행동 테스트 시간은 제외합니다.
총 토큰과 실제 과금도 같지 않습니다. CLI가 비용을 제공하지 않아 비용은
`null`로 남겼습니다. 한 번의 확률적 실행으로 전체 성능을 일반화할 수 없습니다.

근거: [원본 해시와 정제한 비교 기록](artifacts/v37/pet-pair-v36.json).

### 중단된 후보를 따로 검사하니 실제 결함도 있었습니다

원래 후보를 수정하지 않고 새로운 임시 clone에 독립 테스트를 적용했습니다.
기본 수정 동작 4개는 통과했지만, 다른 소유자의 항목을 수정/재연결하지
않아야 하는 테스트 1개는 실패했습니다. 같은 검사에서 기존 코드의 회귀가
재현되고, 정답 변경은 5개를 모두 통과했습니다.

이는 컨트롤러 직접 호출과 JPA 저장 행에 관한 회귀입니다. 실제 HTTP 요청의
인증 우회 공격을 입증한 것은 아닙니다. 사후 검사는 최초 성공률에 합산하지
않았으며, 이 후보를 승인하거나 회사 코드에 적용하지 않았습니다.

근거: [사후 독립 검사](artifacts/v37/pet-posthoc-oracle.json).

## 왜 v36의 차단을 그대로 둘 수 없었나

다른 실제 작업 `spring-01-pet-association`은 이미 저장된 항목도 중복 없이
연결하도록 바꾸는 요구사항입니다. 역사적 정답 코드조차 기존 `isNew` 조건과
달라 v36은 검토 대상으로 감지했습니다. 감지 자체는 맞지만, 그것을 무조건
구현 실패로 취급하면 정당한 기능 변경을 마칠 수 없습니다.

근거: [기존/정답 커밋과 반례](artifacts/v37/authorized-change-counterexample.json).

### 실제 Java 프로젝트로 수정된 실행 흐름 확인

동일한 `spring-01-pet-association`의 알려진 정답 변경을 새 임시 clone에서
결정적으로 재생했습니다. **모델 호출 0회, 재생 1회**이며 AI 평가가 아닙니다.

- 실제 Maven 필수 테스트 76/76 통과.
- 작업 상태는 `implementation-needs-review`로 남음.
- 검토 없이 apply하면 `apply_preservation_review_required`로 거부.
- 현재 후보의 fingerprint를 명시해 임시 clone에 적용 성공.
- 적용한 소스에서 다시 실제 테스트 76/76 통과.

회사 원본이나 운영 데이터는 사용하지 않았습니다. 자동 구현 품질과 구분해
[재생 기록](artifacts/v37/authorized-target-replay.json)을 남겼습니다.
재현: `node docs/evidence/artifacts/v37/replay-authorized-target.mjs <spring-petclinic-bare-mirror>`.
공개 저장소 mirror와 호환되는 JDK/Maven 캐시가 필요하며 임시 clone을 만듭니다.

## v37의 동작

1. 기존 관계 변경 조건을 조사합니다. 이 관찰을 불변의 팀 정책으로 간주하지 않습니다.
2. 조건이 바뀌어도 필수 테스트를 실행합니다. 진짜 테스트 실패만 기존 횟수 안에서 복구합니다.
3. 테스트가 통과하고 조건 변경이 남으면 `implementation-needs-review`로 표시합니다.
4. 적용 전에 현재 후보와 원본, 검증 기록의 봉인, 파일 목록을 다시 확인합니다.
5. 사람이 정확한 diff를 본 다음 현재 fingerprint와 검토 메모를 명시해야 적용합니다.
6. 원본/후보가 달라졌거나 검사가 미완료이면 그 승인으로 적용할 수 없습니다.

`record.status: passed`는 기존 호환성을 위한 **필수 검증 통과**입니다.
별도의 `preservationReview` 및 work 상태가 승인 대기를 표시합니다.
과거 봉인 기록은 덮어쓰지 않고 현재 기준 검토 결과를 별도로 계산합니다.

검토 메모는 12–512자 한 줄이며 탐지 가능한 비밀값/개인정보를 거부합니다.
승인 fingerprint, actor, 메모는 적용 영수증에 남습니다. 이것은 명시적인
판단 기록이지 의미적 정확성/보안 증명이나 인증 서버는 아닙니다.
파서가 모르는 별칭, 상속, 파일 간 흐름 등의 제한은 여전히 남아 있습니다.

## 남은 목표

서로 독립적인 백엔드 3개·대표 작업 20개의 실제 모델 비교라는 완료 기준은
변경하지 않았습니다. 역사적 비교와 서로 다른 런타임 결과를 합쳐 하나의
성공률로 내지 않습니다. 이번 구조 검토 보완은 전체 구현 품질 문제의
해결이나 OMO 대비 우월함을 증명하지 않습니다.

추가 실제 방문 날짜 작업에서는 BTH의 첫 구현이 Java 포맷 검사에 실패해
테스트 실행 전 중단됐습니다. 서식 때문에 모델에게 다시 일을 시키는 비용과
프로젝트가 선언한 포맷 도구를 안전하게 실행할 수 있는지 후속 개선 대상으로
남깁니다. 평가 조건을 사후 변경하거나 이 실패를 PASS로 바꾸지 않습니다.

[20개 작업 현황](artifacts/v37/corpus-ledger.json): 독립 행동 검사 정의 11개,
현재 정의와 일치하는 기존/정답 검증 10개, 역사적 양쪽 모델 추론 기록이 있는
서로 다른 작업 8개, 양쪽 모두 첫 시도에 성공한 적이 있는 작업 3개입니다.
이 숫자는 서로 다른 버전의 **증거 보유 현황**이지 8개를 합친 성공률이 아닙니다.

다음 우선순위는 (1) 프로젝트가 선언한 서식 도구의 안전한 적용 가능성,
(2) 과도한 입력/탐색 비용과 영향 후보 누락, (3) 테스트·수정까지 맡기는
자연스러운 직접 CLI 기준선, (4) 아직 없는 작업별 행동 검사입니다.
